# Artroom: plan for end-user documentation

2026-10-03. Revision 3. The complete documentation plan, updated for
declared acts and Hugh's current priority order: acts that enable the
jam, any spikes that unblock it, then jam development and Artroom docs
in parallel. Request `93c76c16`, promise `938dc408`.

The earlier Workers AI default for pi-durable is retained. This revision
does not adopt an issue-tracking design, a documentation host or a
vocabulary freeze. It prepares the documentation handoff for review.

**The goal.** A new reader, person or agent, understands Artroom and
lands a first change without help. When readability for new users
conflicts with completeness, brevity of our effort or technical
precision, readability wins. Precision moves to the reference pages,
which link to the protocol.

This note covers:
- what the current plans say about documentation, and what is missing;
- who the readers are;
- the readability standard, and how we test it;
- the full set of pages, in four parts:
  - A: Artroom as an issue tracker;
  - B: Artroom for design and development;
  - C: running agents, on any harness and infrastructure;
  - D: architecture and extensibility;
- the product decisions the documentation depends on;
- staging, ownership and acceptance.

Section 10 lists the decisions still open. Section 9 gives the delivery
order; its dates are the original plan's targets, not reasons to cut
scope or hold the jam behind unrelated documentation work.

8. **No readability test.** Nothing checks that a new reader succeeds.

## 3. The readability standard

We follow ISO 24495-1 (plain language): readers find what they need,
understand it, and can use it. In practice:

**Writing rules:**
1. **Start with the reader's task.** The first paragraph says what the
   page helps you do, and who it is for.
2. **One idea per page.** A page that needs two headings at the top
   level is two pages.
3. **Plain words.** Short sentences, active voice, everyday words. A
   technical term is defined where it first appears and in the glossary.
4. **Few terms to start.** The code-review quickstart introduces room,
   member, claim, lane, proposal, review, check, land, policy and attention
   queue as the example needs them. Other applications use their own
   vocabulary. Explain declaration and binding when an application
   builder prepares an act; explain lease, generation, obligation,
   carry and reservation only where needed.
5. **Show, then explain.** Each how-to page opens with the commands or
   code, then explains them.
6. **Every example runs.** Commands and code on every page are tested
   against a real room on each release (section 8).
7. **Say what can go wrong.** Each how-to page ends with the likely
   refusals and their fixes, taken from the refusal catalogue.
8. **Facts, not claims.** Comparisons with other products are factual
   and qualified, as the plan requires. Unmeasured numbers are labelled.
9. **Planned features are labelled.** A page about something not yet
   built says "planned" at the top.

**Tests of readability:**
- **The cold-reader test (people).** Someone who has never seen Artroom
  follows the Quickstart on a fresh machine. We record where they stop
  and how long it takes. Target: a first change landed in 15 minutes
  on the hosted instance, with no help.
- **The cold-agent test (agents).** A fresh agent session on each
  supported harness gets only the agent guide and a task. It must
  perform the code-review loop without reading the protocol. An
  additional test gives it an unfamiliar application declaration and
  asks it to discover and perform that act without a hard-coded tool.
  We record its tokens, refusals and turns; success requires both the
  intended result and the expected permission boundaries.
- **A style check** in CI (for example Vale, with a plain-language rule
  set), for sentence length, passive voice and banned jargon.
- **checker reviews each page** for accuracy and plain language, like
  any other change.

## 4. The structure

The pages follow the four kinds of documentation of the Diátaxis
framework, so a reader always knows what kind of page they are on:

| Kind | Purpose | Example |
|---|---|---|
| Tutorial | Learn by doing, start to finish | Quickstart |
| How-to | Do one task | Connect Codex to a room |
| Explanation | Understand why | Why acts are signed |
| Reference | Look something up | Refusal codes |

The documentation lives in `docs/` in the repository, as Markdown. The
proposed site serves it from the same Worker as static assets, so the
hosted instance carries its own manual. That host is still a proposal;
section 7, D3 covers it. Markdown pages can be reviewed before the host
is chosen.

## 7. Product decisions the documentation depends on

### D1. Issue tracking

**The gap.** The legacy claim is held by its author, with a lease and
workspace. Unheld addressed items and completion without landing remain
undelivered. Under declared acts, the workroom vocabulary may evolve
during self-hosting; assess which capability needs a platform primitive
and which belongs in declarations before amending the platform.

**Option 1, retained proposal: open items as unheld lanes.** The earlier
design proposed the following. It is not adopted by this plan. Reconcile
its behavior with the declared-acts model, assign a free amendment number
only if a contract change is needed, and get independent review before
implementation:
- **`claim` with `hold: false`** opens an unheld lane: a goal, an
  optional scope, and an optional addressee (a role or member). It
  appears in the addressee's attention queue. Overlap is computed when
  it is filed, so the plan's first idea, "declared intent before code",
  reaches the backlog too.
- **Take-over** (R-LANE-7) already lets any member whose role may claim
  pick up an unheld lane. That becomes "pick up this item".
- **`release` gains an outcome:** `done-elsewhere`, `wont-do` or
  `duplicate-of <lane>`, with a note. A closed lane cannot be taken
  over.
- **Nothing else changes:** no labels, priorities or custom fields in
  the first build. Scope, goal text and the addressee are the filters.

This touches lane A (admission and attention), lane E (one CLI command
and one MCP tool option), lane F (a filter on the Room screen) and lane
L (two new body fields in the log format).

**Option 2: document today's pattern.** Claim, then release at once with
a note; the lane becomes unheld and can be taken over. It needs no
protocol change, but it holds a lease and opens a workspace for work
nobody is doing, needs a scope before anyone understands the work,
cannot be addressed to someone, and cannot be closed. Part A would then
be one honest page, "Tracking work elsewhere and linking it", rather
than an issue tracker.

**Judgment.** Option 1 would make Part A straightforward, but its complete
authority and lifecycle design is still needed. Option 2 documents a
limited delivered workflow; it cannot justify claiming the undelivered
issue-tracking features. Neither option is a mandatory jam-start gate.
Builder records how the first development task tracks work, review and
acceptance; planner keeps the richer work-tracking scope owed.

### D2. Harness support

The guides in C2 promise that each harness works. Each needs a
**cold-agent test** passing before its guide is published:
- Claude Code, Codex and pi: the MCP route, and the CLI route for pi.
- pi-durable: hugh asked (2026-10-01) for a fuller integration than a
  connection guide, because its capabilities fit Artroom closely. It
  gets its own design note and spike, outside this plan. Questions for
  that design include:
  - agents as pi-durable conversations in Durable Objects, next to the
    Room, calling it over a service binding;
  - the Room's attention queue and subscriptions waking or steering
    conversations (pi-durable's `whenBusy: "steer"`);
  - lane state held as a pi-durable durable document, updated in the
    same commit as the transcript;
  - pi-durable's ownership tree matched to lanes, so aborting a lane's
    work and releasing the lane agree;
  - forked conversations per generation or per reviewer;
  - approval hooks that wait for an Artroom review or a person's act,
    rather than an approval kept only inside the harness;
  - exactly-once mapping between pi-durable's `requestId` and Artroom's
    `idempotencyKey`, and which tools are safe to replay;
  - people watching and steering agents from the Room's web UI.

  - inference on Cloudflare Workers AI by default (hugh, 2026-10-01),
    with the API token permissions it needs.

  The pi-durable guide in C2 documents what that design delivers.

### D3. The documentation site

Recommended: Markdown in `docs/`, rendered by a small static site
generator into the Worker's static assets, so the hosted instance serves
`/docs`. No separate hosting.

## 8. Acceptance

The documentation is complete when:
1. Every delivered capability has the section-4 pages it needs. A page
   for an undelivered capability says "planned" and names its owner;
   that placeholder does not count as completed documentation for the
   capability. Keep the full page inventory owed.
2. Every command and code sample runs in CI against a test room.
3. The cold-reader test passes: a first change landed in 15 minutes on
   the hosted instance, recorded, by someone new to Artroom.
4. The cold-agent test passes on Claude Code, Codex and pi, and the
   pi-durable spike reports.
5. The reference pages for the CLI, MCP tools, refusals and errors are
   generated, and CI fails if they drift from the contract.
6. The style check passes on every page.
7. checker has approved each page for accuracy and plain language.
8. The unfamiliar-application cold-agent test passes; declaration
   changes, stale intent, retirement and name reuse are explained with
   working examples. Each page states the tested release and separates
   legacy behavior from delivered v2 behavior and planned work.
