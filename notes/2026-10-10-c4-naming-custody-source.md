`packages/page/src/naming-custody.ts` defines the closed naming context, presentation projection, confirmed proposal, exact envelope and journal. A usable sample carries the trusted origin, full directory and membership references, enrolled member, public key, credential reference and generation, database epoch, native definition, head/time and proved profile absence or actual profile ID/revision/opening/name. Unsupported and unavailable presentation states are separate; an optional last sample is explicitly stale. A local sample shape check establishes no native authority. The future native adapter must authenticate its reads, verify the directory's actual membership relationship and current enrollment, and allow only its reviewed supported native pins. Legacy pins are not upgraded here.

`confirmNaming` bounds the raw draft, refuses invalid scalars and controls before trim, then returns an owned confirmed proposal. There is no normalization or truncation. Authoritative capture occurs again under locks and must agree with the frozen profile and definition. It can advance the sampled head without changing that profile; it cannot silently change the expected revision or name. Clearing proved absence or saving the same sampled name is a local no-op. Native grants and the server's final judgment remain authoritative, including ordinary reusable grant-window qualifications; this source adds no human-only condition or instantaneous revocation claim.

`NamingCustody` acquires exclusive locks in credential-reference, logical enrolled-room context, then naming-operation order. The logical slot includes the origin and full room/member identity, rather than the current key/generation, so replacing a credential cannot hide an unresolved original. It holds these locks through credential resolution, authenticated capture, signing, durable preparation/readback, attempted-state retention, POST and known-answer retention. It checks the owner context and credential generation after relevant awaits and immediately before delivery. The constructor, confirmation, native capture and stored values are owned copies.

The first durable record is definitely unsent and contains the exact signed intent, grants, beside fields, idempotency key and frozen proposal. Naming has no declared detached/presented/value side inputs; undeclared fields are refused. A second durable CAS records attempted state before POST. Unknown, mismatched, malformed or accepted-but-unverified originals block any replacement signature. `resumePrepared` is a separate explicit action for the exact definitely-unsent original after current capture/revision checks. `reconcile` never POSTs or signs: not-found is still unknown, and idempotency mismatch is quarantined.

Every complete first Answer is loaded before awaited persistence or proof work. If saving it fails, the loaded operation keeps the whole reply and exact original, the preceding durable journal remains, and that instance blocks new preparation, replacement and retry. Reload reads the attempted original and settles only its signed identity; it cannot invent the lost reply or classify that original as unsent. An unavailable first Answer remains intact when original settlement later supplies a complete accepted receipt: settlement is separate evidence, not a rewrite of the first reply.

The public status distinguishes accepted-unverified, recorded-verified and an independent current read. Recorded-verified requires matching full receipt scope/pin/intent, retained entry hash and exact signed bytes, effects, epoch and send identities. This is correspondence with an authenticated entry, not a new semantic replay or ancestry verifier. Latest-name reads can be unavailable or conflicting and never verify acceptance. The native adapter must preserve the trusted service origin and original context, reject redirects/foreign responses, bound complete reads and retain actual native refusal reasons. It is intentionally not implemented by this custody source.

`packages/page/src/naming-indexeddb.ts` owns one naming-only IndexedDB namespace with meta, nonextractable credentials, retained contexts and naming journals. The private Ed25519 key is persisted as a nonextractable CryptoKey; resolution verifies its public-key identity and signing pair and returns a signer, not the key. The context catalog stores credential references and legitimately enrolled full contexts. It is local metadata, not enrollment proof or a cross-device directory. It stores no invitation secret, session token, founding record, voice transcript or general outbox record.

The owner supplies explicit positive limits for credentials, contexts, records per journal, canonical bytes per record and aggregate logical serialized metadata. There is no guessed 64-context default, eviction or claim about physical disk overhead. Each journal commit uses one IndexedDB read/write transaction: validate the old whole journal, compare revision and bytes, validate the legal original-preserving transition, put, enforce quotas, read back, then await completion. Any transaction failure aborts that write. Only IndexedDB requests are awaited inside transactions; crypto, locks and network work occur outside. New preparation/dispatch requires the current credential binding; exact original receipt recovery may continue after generation invalidation. Local invalidation retains keys and journals and claims no native revocation.

`create` is an explicit first-domain action. Reload uses the retained name/origin/epoch with `restore`; missing storage, wrong epoch, inaccessible storage, malformed or missing journals block recovery rather than creating an empty replacement. An existing context whose journal has disappeared cannot recreate it through `retainContext`. A blocked database open rejects once, aborts a later upgrade and closes a late success handle. Deleted browser storage cannot recover deleted bytes by itself: explicit re-enrollment or external original custody is a separately owned recovery path, never permission to refound or resend.

`publicStatus` is an explicit whitelist of phase, persistence availability, current-read status and intent digest. Draft/name text, credentials, keys, grants, signed envelopes, known Answer bodies, session headers and the context catalog remain private. Evidence for future runs must preserve raw private logs separately and publish only a reviewed result whitelist.
