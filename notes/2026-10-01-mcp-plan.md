# Artroom: MCP plan

2026-10-01. Revision 3: hugh's decisions (section 14), and a
correction to the staging of item 5. Request
`489a992e`. Answers hugh's request for an
explicit MCP plan that is concrete, comprehensive, layered, and flexible
enough for general Artroom applications.

**What this note decides.** How agents and people reach a room through
the Model Context Protocol (MCP): the layers, every tool, resource and
prompt, authentication, statelessness, live updates, errors, retries,
context cost, client support, and how an application adds its own tools
without changing the core.

**Kinds of statement.** MCP facts come from the specification and
vendor documentation (section 14), as of 2026-10-01. Facts about
Artroom come from `main` at `8189d66` and lane E's branch
`request/laneE-clients` at `69734d4`. Judgements are marked
**Judgement**; claims nobody has tested are marked **Untested**.

## 1. Summary

- **MCP is a transport, never an authority.** Every MCP call becomes a
  `RoomApi` call, judged by the room at admission like any other act.
  MCP adds no rule, no role and no shortcut.
- **Five layers.** A transport adapter, a core profile, role toolsets,
  application packs and composed application servers (section 4). Each
  layer uses only the one below it.
- **Tools are complete; everything else is an enhancement.** An agent
  that sees only tools can do everything its role allows. Resources,
  prompts, elicitation, tasks and UI apps make things easier where a
  client supports them, and are never required.
- **Stateless, on the 2026-07-28 specification,** with the legacy
  stateless mode for clients that do not speak it yet (Codex by default,
  and pi). All state lives in the room, reached by handles: lane and
  lease, operation IDs and cursors.
- **Polling, not push, for agents.** `attention` gains a bounded wait.
  Live, real-time applications use the room's WebSocket, not MCP.
- **Applications extend MCP in two ways.** Declarative tool packs kept
  in the repository (no code runs in the room), or their own MCP server
  built from Artroom's published MCP library.
- **First, ship what exists.** Lane E's ten tools are built and tested,
  but no Worker serves the MCP endpoint, and the adapter that serves it
  has no owner. That is the first task (section 12, stage 0).

## 2. What exists today

### In the protocol and contract

| Item | Where | What it says |
|---|---|---|
| Ten tools | R-API-9 | `claim`, `workspace`, `renew`, `release`, `propose`, `note`, `review`, `land`, `attention`, `explain`, each calling the `RoomApi` method of the same name |
| Endpoint | R-CRED-10, `HttpRoutes` | `POST /v1/rooms/:room/mcp`, Streamable HTTP. The only HTTPS route that accepts a bearer for acts |
| Credentials | R-CRED-3, R-CRED-9 | A bearer token from a room-custody invitation, shown once. The room signs with a session key under a delegation |
| Never over MCP | R-CRED-10 | `roster`; `check` (RPC only) |
| Errors | R-API-1 | Refusal: `isError: false`, structured `Refusal`. Failure: `isError: true`, structured `ArtroomError` |
| Live updates | R-API-8 | "MCP: `attention` with the cursor" |
| Workspace grant | R-WS-5 | `grant` only when the workspace is ready |
| No token leaks | R-WS-4 | No token in logs, attention, errors or caches |
| Descriptors | `transports.ts` | `McpToolDescriptor {name, description, inputSchema, outputSchema, method}`; no annotations; the tool set is closed |

### In lane E's server (`packages/mcp`, not yet on main)

- Built on `@modelcontextprotocol/server` 2.0.0 and the Agents SDK's
  stateless `createMcpHandler` (agents 0.24.0). A new server per
  request; no sessions.
- Two transports: Streamable HTTP (the Worker) and stdio (`artroom mcp`,
  signing with the user's own key).
- Bearer authentication from the `Authorization` header. 401 with
  `WWW-Authenticate: Bearer realm="artroom"`.
- Ten tools with closed input schemas, refusal guidance in each
  description, and server instructions describing the loop.
- 27 tests, including workerd, stdio, token-leak and idempotent-retry
  tests.

### What is missing

1. **No deployed endpoint.** No Worker routes `/v1/rooms/:room/mcp`.
   Amendment 2 says the adapter "belongs to whichever lane wires the
   deployment", and none does.
2. **Tools only.** No resources, prompts, annotations or titles.
   `outputSchema` exists in the descriptors but is not advertised.
3. **Thin reads.** An agent cannot read a lane, a proposal's
   obligations, a file at a proposed head, or the room's policy, except
   by `explain` on an act ID it already knows.
4. **No waiting.** `attention` returns at once, so agents poll in a
   loop or stop.
5. **One tool set for every role.** A reviewer sees `land`; a triager
   sees `workspace`.
6. **No extension point.** The tool set is closed in the contract and
   in the server. An application cannot add a tool.
7. **Bearer only.** Hosts where a person cannot set a header (Claude
   Desktop and web, ChatGPT) cannot connect.
8. **No context budget** and no test of it.

## 3. The MCP landscape this plan targets

**Specification 2026-07-28** (final; nothing newer pending):
- **No sessions and no `initialize`.** Each request carries its
  protocol version and client capabilities. `server/discover` is
  required. State across calls uses server-minted handles passed as
  ordinary arguments.
- **Lists are stable.** `tools/list`, `resources/list` and
  `prompts/list` must not vary by connection or by earlier requests.
  They may vary by the authorization on the request.
- **Results carry `ttlMs` and `cacheScope`.**
- **The server cannot call the client.** Elicitation is a result of
  type `input_required`, answered by the client retrying.
- **Push is narrow.** One mechanism remains, `subscriptions/listen`,
  for list changes and resource updates. Nothing is replayed after a
  disconnect.
- **Sampling and roots are deprecated.** Logging is deprecated.
- **Extensions:** Tasks (`io.modelcontextprotocol/tasks`) for
  long-running calls; MCP Apps (`io.modelcontextprotocol/ui`) for UI in
  hosts.
- **Authorization:** OAuth 2.1, Protected Resource Metadata (RFC 9728),
  audience-bound tokens (RFC 8707), client ID metadata documents
  preferred, dynamic registration deprecated.

**Cloudflare:** `createMcpHandler` is the stateless path; `McpAgent` is
deprecated and frozen. Its notifications are isolate-local.
`@cloudflare/workers-oauth-provider` 1.2.1 implements the 2026-07-28
authorization profile.

**Clients on 2026-10-01:**

| | Claude Code | Codex CLI 0.160 | pi 1.0 |
|---|---|---|---|
| Protocol | 2026-07-28 | 2025-06-18 by default; 2026-07-28 behind a flag | Up to 2025-11-25 |
| Bearer header | Yes | Yes, from an environment variable | Yes |
| OAuth | Yes, with CIMD | Yes, with CIMD | Yes, without CIMD |
| Resources | Yes | Through generic resource tools | Through generic resource tools |
| Prompts | As slash commands | Unknown | Unknown |
| Elicitation | Yes | Unknown | No |
| Tool loading | Deferred (tool search) | Deferred | Code mode by default |
| Limits | Descriptions cut at 2,048 characters; output capped at 25,000 tokens; calls over 2 minutes go to the background | Instructions: first 512 characters must stand alone; 60 s tool timeout by default | Text results over 20 KB truncated |
| MCP Apps UI | No | Behind a flag | No |

pi-durable is a framework, not a client; how it reaches a room is the
subject of its own design (request `3f23ea89`). This plan supplies the
pieces it can use (section 9).

**Judgement.** The lowest common denominator is: stateless HTTP, a
bearer header, tools with structured results, and nothing that depends
on push, elicitation, prompts or UI. Section 4's layers are built so
that this floor is complete.

## 4. The layers

```
L4  Application servers   an app's own MCP server, composed from the library    (app's Worker)
L3  Application packs     declarative tools, resources, prompts in .artroom/mcp/ (room's MCP Worker)
L2  Role toolsets         which tools a caller sees, by role and delegation      (room's MCP Worker)
L1  Core profile          tools, resources, prompts over RoomApi                 (room's MCP Worker)
L0  Transport adapter     wire format, auth, errors, caching, limits             (room's MCP Worker)
    ─────────────────────────────────────────────────────────────────────────
    RoomApi (contract)    admission, authority, policy, the log                  (Room Durable Object)
```

| Layer | Owns | Must not |
|---|---|---|
| **L0 Transport** | 2026-07-28 and legacy stateless wire formats; HTTP and stdio; bearer and OAuth; mapping refusals and errors; `ttlMs` and `cacheScope`; output size limits; token redaction | Know any tool's meaning |
| **L1 Core** | The core tools, resources and prompts, each a thin call to one `RoomApi` method; schemas; annotations; descriptions with fixes for likely refusals | Hold state between calls; decide authority; combine acts |
| **L2 Roles** | Choosing which L1 and L3 tools a caller sees, from its role and delegation kinds, so lists vary only by authorization | Grant anything; a hidden tool called anyway is still judged by the room |
| **L3 Packs** | Tools, resources and prompts an application declares as data in the repository, each mapping to one L1 call | Run code; make a new act kind; bypass policy |
| **L4 App servers** | An application's own MCP endpoint, with its own state and code, calling the room through the client library under a delegation | Write to the room except through `RoomApi` |

**The rule that keeps layers honest:** every write, at every layer,
ends as one signed act admitted by the room. MCP never composes several
acts into one call.

## 5. L0: the transport adapter

**Wire formats.** `createMcpHandler` with `legacy: "stateless"` serves
2026-07-28 clients and older stateless clients from the same endpoint.
No session store. `server/discover` advertises the server's name,
version, instructions and capabilities.

**Endpoints.**
- `POST /v1/rooms/:room/mcp`: the room's MCP endpoint, as today. One
  room per URL keeps tool lists stable per principal and lets OAuth
  bind tokens to one room.
- stdio: `artroom mcp`, for local clients signing with the user's own
  key (exists).

**Authentication.**

| Method | For | How |
|---|---|---|
| Bearer header | Agents in Claude Code, Codex, pi, scripts | As today: a room-custody invitation, redeemed once; the token in `Authorization: Bearer`. Each harness keeps it in an environment variable or header helper, never in a committed file |
| OAuth 2.1 | People in hosts that cannot set headers: Claude Desktop and web, ChatGPT | `workers-oauth-provider`. The room's join page is the consent page: redeeming an invitation issues an audience-bound token for that room's MCP URL. Protected Resource Metadata at the standard well-known path; 401 with `resource_metadata`. CIMD preferred; dynamic registration only for clients without CIMD (pi) |
| Own key (stdio) | A person or script with an Ed25519 key file | The CLI signs envelopes; no bearer |

Unchanged: roster acts are never accepted over MCP; `check` stays RPC
only; tokens are never passed through to Artifacts or logged (R-WS-4).

**Errors.** As R-API-1, with three additions:
- **Advertise `outputSchema`** for every tool. Each is `oneOf` the
  tool's result and `Refusal`, so structured content always conforms,
  as the 2026-07-28 specification requires.
- **Every result also carries a short text form** (the headline and
  fix, as lane E does), because some clients show only text.
- **JSON-RPC errors are only for protocol faults** (bad JSON, unknown
  method).

**Caching.** Lists: `ttlMs` of one hour, `cacheScope` private, since
they vary by authorization. Reads of immutable things (an act, a
generation, a file at a commit): long TTL. Reads of moving things
(attention, a lane's state): `ttlMs: 0`.

**Size.** Every result stays under 20 KB of text (pi's limit, the
smallest). Lists paginate with cursors; diffs and files return a
bounded slice with a "more" cursor and a note saying so.

## 6. L1: the core profile

### Principles

1. **One tool per `RoomApi` method;** names match the API, so a reader
   of the docs, the CLI and the MCP tools sees one vocabulary.
2. **Short names, no prefix.** The host already namespaces them (for
   example `mcp__artroom__claim`).
3. **Annotations tell hosts what is safe.** Hosts may auto-approve
   read-only tools and ask before consequential ones.
4. **Retries are safe.** Every act tool takes an `idempotencyKey`.
   **Proposed change:** make it required, so a retry after a lost
   response can never record an act twice. The description says "any
   unique string; reuse it to retry this exact call".
5. **Descriptions are for agents.** Each says when to use the tool, the
   one or two likely refusals and their fixes, and stays under 1,000
   characters.
6. **Handles, not sessions.** Lane and lease (`McpHeld`), operation
   IDs, cursors and act IDs are passed in arguments.

### Tools

Act tools (write):

| Tool | Input (abridged) | Result | Annotations |
|---|---|---|---|
| `claim` | `goal`, `scope[]`, `plan?`, `because?[]`; for a rescope or take-over: `lane`, `lease?`, `expectedGeneration`; `hold?` (if D1 of the documentation plan is adopted); `idempotencyKey` | `Claim` with overlaps, or `Refusal` | not read-only, not destructive, idempotent |
| `propose` | `lane`, `lease`, `head`, `expectedGeneration`, `summary`, `because?[]`, `idempotencyKey` | `Proposal` with obligations and preview state | not read-only, not destructive, idempotent |
| `note` | `anchor` (act, or path and line at a head), `text`, `replyTo?`, `idempotencyKey` | Receipt | not read-only, not destructive, idempotent |
| `review` | `lane`, `generation`, `head`, `verdict`, `scope[]`, `dependsOn?[]`, `text`, `idempotencyKey` | Receipt with obligations met | not read-only, not destructive, idempotent |
| `land` | `lane`, `lease`, `generation`, `head`, `waitMs?`, `idempotencyKey` | Landing operation and its state | not read-only, **destructive** (it changes main), idempotent |
| `release` | `lane`, `lease`, `note?`, `outcome?` (if D1), `idempotencyKey` | Receipt | not read-only, **destructive** (gives up the lease), idempotent |
| `renew` | `lane`, `lease`, `idempotencyKey` | New expiry | not read-only, not destructive, idempotent |

Request tools (signed requests, not acts):

| Tool | Input | Result | Annotations |
|---|---|---|---|
| `workspace` | `lane`, `lease`, `waitMs?` | Operation; `grant` (remote, token, expiry) only when ready | not read-only, not destructive, idempotent |

Read tools. `attention` and `explain` exist. `lanes`, `lane`,
`proposal` and `operation` are new as tools but call existing `RoomApi`
methods (`lanes`, `lane`, `proposal`, `op` and `wait`). `room`, `diff`,
`file` and `policy` need new `RoomApi` reads (amendment item 5), marked
"(item 5)":

| Tool | Input | Result | Annotations |
|---|---|---|---|
| `room` (item 5) | none | Who you are (member, role, delegation kinds and expiry); the room's name, policy version, lease duration, `publishedThrough`; your held lanes. The first call an agent makes | read-only |
| `attention` | `cursor?`, `limit?`, **`waitMs?`** (new: up to 45 s, under Codex's 60 s default timeout) | `AttentionPage`; returns early when an item arrives | read-only |
| `lanes` | `filter` (state, holder, scope glob, text), `cursor?`, `limit?` | Lane summaries | read-only |
| `lane` | `lane` | Claim, holder, lease, generations, overlaps, landing operation | read-only |
| `proposal` | `lane`, `generation` | Changed paths, obligations, evidence (reviewed here, carried, stale), preview state, notes | read-only |
| `diff` (item 5) | `lane`, `generation`, `path?`, `cursor?` | A bounded diff against the integration base | read-only |
| `file` (item 5) | `path`, `at` (a pinned head, a commit or `main`) | File content, bounded, with a cursor | read-only |
| `policy` (item 5) | none | The active policy in plain English, with its version | read-only |
| `explain` | `act` | Rules applied, inputs, outcome; or `not-found` | read-only |
| `operation` | `id`, `waitMs?` | The state of a workspace, preview or landing operation | read-only |

That is 18 tools: 14 on today's `RoomApi`, and 4 more with item 5. The context budget (section 10) limits what each
role sees at once.

**Why `diff` and `file` matter.** Reviewers, triagers and application
agents (a jam player's coach, a documentation reviewer) should not need
a git checkout to read what they judge. Both read through the room's
read session from the canonical repository at a pinned head; neither
can see a fork.

### Resources

Resources give hosts that support them (Claude Code's `@` mentions) a
browsable view. Every resource has a read tool with the same content, so
nothing depends on resource support.

| URI template | Content | Tool equivalent |
|---|---|---|
| `artroom://room` | Room summary | `room` |
| `artroom://lane/{lane}` | Lane | `lane` |
| `artroom://lane/{lane}/generation/{n}` | Proposal | `proposal` |
| `artroom://act/{act}` | Explanation | `explain` |
| `artroom://policy` | Active policy | `policy` |
| `artroom://file/{at}/{+path}` | File at a commit | `file` |

### Prompts

Prompts are ready-made instructions a person can pick (Claude Code shows
them as slash commands). They contain no logic.

| Prompt | Arguments | Use |
|---|---|---|
| `start` | none | Read `room` and `attention`, then follow the loop for your role |
| `work-on` | `goal` | Claim, get a workspace, change, propose |
| `review` | `lane`, `generation` | Read the proposal and diff, then review with scope and `dependsOn` |
| `triage` | none | Work through the attention queue |
| `handover` | `lane` | Write a handover note and release |

### Server instructions

At most 512 characters, self-contained (Codex keeps only that much):
what the room is, "call `room` first, then `attention`" (only
`attention` until item 5 ships), and that
refusals carry a fix. Longer guidance lives in the `start` prompt and
the agent guide.

### Long operations

`workspace`, `land` and `operation` take `waitMs` (at most 45 s) and
return the operation's state; the caller calls `operation` again to keep
waiting. Operation IDs are designed to map one to one onto the Tasks
extension when clients support it (stage 3), with no change to their
meaning.

### Elicitation

Not used for authority. A verdict, a landing or a claim is always an
act by its signer, never a click inside a host. The one planned use is
convenience: a person using a host with elicitation can be asked to
pick among overlapping lanes before a `claim` (stage 3). Clients without
elicitation get the same choice as a refusal with a fix.

## 7. L2: role toolsets

The tool list varies only by the caller's authorization, which the
2026-07-28 specification allows. A hidden tool that is called anyway is
judged by the room as usual; hiding saves context, it is not security.

| Toolset | Default for | Tools |
|---|---|---|
| `builder` | role `agent`, `member` | `room`, `attention`, `claim`, `workspace`, `propose`, `note`, `land`, `release`, `renew`, `lane`, `proposal`, `explain`, `operation` (13) |
| `reviewer` | members named by review obligations | `room`, `attention`, `lanes`, `lane`, `proposal`, `diff`, `file`, `note`, `review`, `explain` (10) |
| `triager` | issue tracking, if D1 is adopted | `room`, `attention`, `lanes`, `lane`, `claim` (unheld), `note`, `release` (close), `explain` (8) |
| `observer` | read-only sessions | `room`, `attention`, `lanes`, `lane`, `proposal`, `diff`, `file`, `policy`, `explain` (9) |
| `all` | admins and maintainers, or on request | All 18 |

Tools marked "(item 5)" in section 6 join their toolsets when item 5
ships.

**How a caller chooses.** The invitation names a toolset; a delegation
may narrow it. A client may also connect to
`/v1/rooms/:room/mcp?toolset=reviewer` to see fewer tools than it is
allowed. A toolset can never add a tool the caller's delegation kinds
forbid.

## 8. L3: application packs

**The problem.** The jam room and other applications want their own
verbs: "join a part", "send a cue", "propose a take". The contract has
seven act kinds and the jam design requires zero contract amendments.
Most application verbs are an existing act with an application's
conventions: a claim on `parts/<part>/**`, a note anchored to the
count-in.

**The design.** A pack is a JSON file in the repository at
`.artroom/mcp/<pack>.json`. Because it is under `.artroom/**`, changing
it needs an admin's approval (R-ADMIN). The room's MCP Worker loads the
packs in the active policy version. A pack declares:

- **Tools.** Each has a namespaced name (`jam.join_part`), a
  description, an input schema in the restricted JSON Schema subset, a
  toolset list, annotations, and a **mapping**: a JSONata expression,
  in the same pinned profile and budgets as policy (R-EVAL), that turns
  the input into exactly one L1 call. For example:

  ```json
  { "name": "jam.join_part",
    "description": "Take a part in the song. Refused if someone holds it.",
    "input": { "type": "object", "required": ["part"],
               "properties": { "part": { "type": "string", "pattern": "^[a-z0-9-]+$" } } },
    "toolsets": ["builder"],
    "call": { "tool": "claim",
              "args": "{ 'goal': 'Play ' & part, 'scope': ['parts/' & part & '/**'] }" } }
  ```
- **Resources.** Read-only URI templates over repository paths, for
  example `jam://song` → `file` of `song.json` at `main`.
- **Prompts.** Templated instructions, for example "you are the bass
  player; listen for cues on the count-in act".

**What keeps packs safe:**
- No code runs; a mapping is a bounded, pure expression.
- Each pack tool makes exactly one L1 call, signed by the caller and
  admitted by the room, so policy, roles and the log treat it exactly
  like the core call. `explain` shows both the pack tool and the core
  act.
- A pack cannot add an act kind, a role or a rule.
- A pack tool's annotations can only be stricter than the core tool's.

**What packs cannot do:** keep state, call other services, or combine
acts. Those belong in an application server (L4).

**Judgement.** Packs cover the verbs the jam note lists without a
redeploy, and they make an application installable by ordinary acts, as
the jam note asks. They do need a contract amendment (section 11),
because today's tool set is closed.

## 9. L4: application servers and the MCP library

An application that needs code, state or other services runs its own
MCP server in its own Worker. To make that quick, lane E's package is
published as a library with separable parts:

| Export | Use |
|---|---|
| `coreTools(room, { toolset })` | The L1 descriptors and runners, bound to a `RoomApi` |
| `packTools(room, packs)` | The L3 tools, for an app that hosts its packs itself |
| `toMcpResult(result)` | The refusal and error mapping of R-API-1 |
| `createArtroomMcpHandler({ room, tools, auth })` | L0, around `createMcpHandler`, with bearer or OAuth |
| `descriptors({ toolset })` | Plain descriptors, for non-MCP harnesses (pi-durable extensions, Agents SDK tools, code mode) |

**Rules for application servers:**
- They reach the room through the client library or a service binding,
  under a delegation the room issued. Every write is a signed act.
- They may re-export core tools next to their own, so an agent needs one
  MCP URL.
- Their own tools are namespaced, and their state is theirs, never
  authoritative over the room (as the jam note already requires of its
  live layer).

**pi-durable** can use `descriptors()` and the runners directly as
pi-durable tools, without MCP; its design (request `3f23ea89`) decides.

**Real-time applications.** MCP is turn-based. A jam player, a live
dashboard or anything that must react within a second uses the room's
WebSocket `subscribe` (R-API-8), as the jam note decides. MCP stays the
connection for turn-based agents and for people in chat hosts.

## 10. Context cost

**The budget.**
- The `builder` toolset's `tools/list` stays under **3,000 tokens**,
  and every other toolset under 2,500.
- Each description stays under 1,000 characters (Claude Code cuts at
  2,048).
- Instructions stay under 512 characters.
- CI measures the token count of each toolset's list and fails over
  budget.

**Why not one "code" tool.** Code mode suits large APIs. Artroom's
surface is small, its acts are signed one at a time, and refusals must
reach the model with their fixes. **Judgement:** plain tools, kept few
by toolsets, are clearer here. `descriptors()` lets a harness that
prefers code mode (pi's default) generate it.

## 11. Contract and protocol changes

One amendment, proposed for checker's review before any lane builds on
it. Working title: **the MCP amendment**.

1. **R-API-9:** the core tools become the 14 of section 6 that call
   today's `RoomApi`, and later the 4 of item 5, in the
   toolsets of section 7. `check` and roster stay excluded.
2. **`McpToolDescriptor`** gains `title` and `annotations`, and
   `outputSchema` is advertised.
3. **`idempotencyKey` is required** on act tools over MCP.
4. **`attention`, `workspace`, `land` and `operation` take `waitMs`,**
   at most 45 s.
5. **New reads in `RoomApi`:** `room` (whoami and summary), `diff`,
   `file` and `policy`, with their MCP tools and toolset places.
   (`lane`, `lanes`, `proposal`, `op`, `wait` and `explain` already
   exist.)
   `diff` and `file` read the canonical repository at pinned heads under
   the read session.
6. **Packs:** `.artroom/mcp/*.json`, its schema, loading at policy
   activation, and the rule that each pack tool maps to exactly one core
   call. The tool set is no longer closed; core names are reserved, and
   pack names must contain a dot.
7. **Toolsets:** an invitation and a delegation may name one.
8. **OAuth:** the join page as the authorization step; Protected
   Resource Metadata; audience binding to the room's MCP URL.
9. **Resources and prompts:** the URIs and prompt names of section 6.

Items 1 to 4 are small and unblock the clients. Items 5 to 9 can follow.
If D1 of the documentation plan (issue tracking) is adopted, its
`hold` and `outcome` fields reach MCP through item 1 with no further
change.
