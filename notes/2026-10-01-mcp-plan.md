## 1. Summary

- **MCP is a transport, never an authority.** Every MCP call becomes a
  `RoomApi` call, judged by the room at admission like any other act.
  MCP adds no rule, no role and no shortcut. A catalogue, an
  annotation, a prompt, a cached schema or a click in a host grants
  nothing.
- **Five layers.** A transport adapter, a core profile, role toolsets,
  application packs and composed application servers (section 4). Each
  layer uses only the one below it.
- **Tools are complete; everything else is an enhancement.** An agent
  that sees only tools can do everything its role allows. Resources,
  prompts, elicitation, tasks and UI apps make things easier where a
  client supports them, and are never required.
- **The code-review tools are one application's vocabulary.** The seven
  named acts (`claim`, `propose`, `note`, `review`, `land`, `release`,
  `renew`) belong to the code-review application. They are not the
  permanent list of kinds. An application that declares its own acts
  reads them with `acts` and submits them with `act`, using tools alone
  (section 4).
- **Stateless, on the 2026-07-28 specification,** with the legacy
  stateless mode for clients that do not speak it yet (on 2026-10-01:
  Codex by default, and pi). The MCP Worker keeps no state between
  calls. State stays with its existing owners and is reached by
  handles: lane and lease, operation IDs and cursors.
- **Polling, not push, for agents.** `attention` gains a bounded wait.
  Live, real-time applications use the room's WebSocket, not MCP.
- **A retry repeats the same prepared call.** Every act tool requires
  an `idempotencyKey`. The key names the retry. The caller, or the
  existing durable owner of the work, keeps the prepared call, so a
  retry never carries a newer meaning under the old key (section 6).
- **Applications extend MCP in two ways.** Declarative tool packs kept
  in the repository (no code runs in the room), or their own MCP server
  built from Artroom's published MCP library.
- **First, ship what exists (History).** On 2026-10-01 lane E's ten
  tools were built and tested, but no Worker served the MCP endpoint,
  and the adapter that serves it had no owner. That was the first task
  (section 12, stage 0). The adapter is now source on `main` and has an
  owner (section 2). Do not commission another endpoint task because
  the old snapshot lacked one.

## 3. The MCP landscape this plan targets

This section is research dated 2026-10-01, with corrections dated
2026-10-03. It is not a statement of what any client does with Artroom.

**Specification 2026-07-28.** Revision 3 called it final, with nothing
newer pending. That was wrong. On 2026-10-03 the official versioning
page calls 2026-07-28 current and says it may receive compatible
changes. The deployed SDK and specification snapshot must be pinned,
and conformance evidence must record the versions accepted.
- **No sessions and no `initialize`.** Each request carries its
  protocol version and client capabilities. `server/discover` is
  required. State across calls uses server-minted handles passed as
  ordinary arguments.
- **Lists are stable.** `tools/list`, `resources/list` and
  `prompts/list` must not vary by connection or by earlier requests.
  They may vary by the authorization on the request.
- **Some results carry `ttlMs` and `cacheScope`.** These are the
  complete results of `server/discover`, `tools/list`, `prompts/list`,
  `resources/list`, `resources/templates/list` and `resources/read`.
  The rule does not make `tools/call` cacheable in general. An interim
  `input_required` result, and a request resumed through
  `inputResponses` or `requestState`, are not cacheable.
- **The server cannot call the client.** Elicitation is a result of
  type `input_required`, answered by the client retrying.
- **Push is narrow.** One mechanism remains, `subscriptions/listen`,
  for list changes and resource updates. Nothing is replayed after a
  disconnect.
- **Sampling and roots are deprecated.** Logging is deprecated.
- **Extensions:** Tasks (`io.modelcontextprotocol/tasks`) for
  long-running calls; MCP Apps (`io.modelcontextprotocol/ui`) for UI in
  hosts.
- **Authorization:** OAuth 2.1, Protected Resource Metadata (RFC 9728),
  audience-bound tokens (RFC 8707), client ID metadata documents
  preferred, dynamic registration deprecated.
- **Structured output must conform.** When a tool advertises an output
  schema, its structured results must conform to it.

**Cloudflare:** `createMcpHandler` is the stateless path; `McpAgent` is
deprecated and frozen. Notification routing belongs to one handler
instance and is isolate-local. A fresh handler made for one fetch
cannot notify a stream that an older handler holds.
`@cloudflare/workers-oauth-provider` 1.2.1 implements the 2026-07-28
authorization profile. It separates sign-in from client consent and
validates safe redirects. Its resource-server handler must enforce
operation scopes. Validating a token gives no Artroom role and no
owner-control policy.

**Clients on 2026-10-01.** This matrix is dated research. Do not read
its flags, exact limits, transport defaults, prompt support, OAuth
coverage or Apps support as current, or as delivered support. Artroom
supports a client when a named client version and configuration has
run as a fresh agent, and the run is recorded (section 13).

|---|---|---|---|
| Protocol | 2026-07-28 | 2025-06-18 by default; 2026-07-28 behind a flag | Up to 2025-11-25 |
| Bearer header | Yes | Yes, from an environment variable | Yes |
| OAuth | Yes, with CIMD | Yes, with CIMD | Yes, without CIMD |

Revision 3 said that Codex keeps only the first 512 characters of the

pi-durable is a framework, not a client; how it reaches a room is the

## 4. The layers

```
L4  Application servers   an app's own MCP server, composed from the library    (app's Worker)
L3  Application packs     declarative tools, resources, prompts in .artroom/mcp/ (room's MCP Worker)
L2  Role toolsets         which tools a caller sees, by role and delegation      (room's MCP Worker)
L1  Core profile          tools, resources, prompts over RoomApi                 (room's MCP Worker)
L0  Transport adapter     wire format, auth, errors, caching, limits             (room's MCP Worker)
    ─────────────────────────────────────────────────────────────────────────
    RoomApi (contract)    admission, authority, policy, the log                  (Room Durable Object)
```

| Layer | Owns | Must not |
|---|---|---|
| **L0 Transport** | 2026-07-28 and legacy stateless wire formats; HTTP and stdio; bearer and OAuth, bound to one room; mapping refusals, tool failures and protocol errors; `ttlMs` and `cacheScope`; output size limits; token redaction | Know any tool's meaning; decide room authority; invent what an act means |
| **L1 Core** | The core tools, resources and prompts, each a thin call to one `RoomApi` method; discovery and submission of declared acts (`acts`, `act`); the code-review conveniences; reads and bounded waits; schemas; annotations; descriptions with fixes for likely refusals | Hold state between calls; decide authority; combine several room acts into one write |
| **L2 Roles** | Choosing which L1 and L3 tools a caller sees, from its current role and delegation and from a narrower choice the caller may make, so lists vary by authorization and the active reviewed configuration, never by connection history | Grant anything; a hidden tool called anyway is still judged by the room. Hiding a tool is not authorization |
| **L3 Packs** | Tools, resources and prompts an application declares as data in the repository, each tool mapping to one ordinary room write or read | Run code; define authority or a rule; declare an act kind (kinds come from the room's declarations, protocol section 33); bypass policy; silently change prepared work |
| **L4 App servers** | An application's own MCP endpoint, with its own state, code and other services, composed from the published client and MCP library, calling the room under a delegation | Write to the room except through `RoomApi`; let application state override a room outcome |

**The rule that keeps layers honest:** every write, at every layer,
ends as one signed act admitted by the room. MCP never composes several
acts into one call.

### The general application route

Revision 3 treated the seven code-review acts as the platform's fixed
vocabulary, and told applications to express their verbs as a `claim`
or a `note`. That is corrected here. The seven named acts are the
vocabulary of the legacy code-review application. An application such
as the jam can declare its own acts under the declarations model
(protocol section 33, on `main`). Its first vocabulary may change while
the application is built in its own room. A pack exposes that
vocabulary. It does not create a second system for defining kinds, and
it does not require every verb to become `claim` or `note`.

A caller that sees only tools must be able to:

1. **Read the acts catalogue.** The active one, and when needed the
   retained catalogue at a historical policy version or sequence. It
   shows each kind, what its target and body require, its executable
   steps, its binding and its guidance.
2. **Choose a declared meaning and prepare it:** `kind`, `target`,
   `body`, `binding` and the required `idempotencyKey`.
3. **Submit that meaning through the general act route.** Admission
   checks the current declaration, authority, delegation map, target,
   body, lease and policy, as for any signed act.
4. **Read the receipt, refusal or operation.** A historical record is
   shown with the meaning retained at its own sequence, even after its
   kind is retired.

Use the `acts` and `act` route of declared-acts stage 5 (**Candidate**,
request `a5d64b35`). A declared application does not wait for dynamic
per-kind tools. Dynamic descriptors are a convenience built from the
same catalogue. Per-kind delegated bindings are still required.
Platform kinds use their own specified routes.

Lists may vary by authorization and by the active reviewed application
configuration. They never vary by the history of an MCP connection.
Reading a historical catalogue does not make a retired kind active
again.

### Checks and roster acts over MCP

Revision 3 said that `check` stays RPC only. That is now true only of
the legacy route. The adopted decision `fa120186` sets the boundary:

- **Bearer roster acts are always forbidden.**
- **The legacy bearer `check` stays RPC-only.** There is no named MCP
  `check` tool. The fixed HTTPS bearer client's legacy `check` and
  `roster` methods refuse before they send anything.
- **A generic `v: 2` act may run a declared check step through MCP,**
  including through the HTTPS bearer client's generic `act` route. This
  holds even when the declared kind has a name other than `check`.
- **The caller supplies the exact binding and key.** The room signs
  with the session key and delegation. It does not choose or replace
  the binding. The delegation's signed grant map must cover the exact
  kind and binding, and the current role and declaration must permit
  the act.
- **Every ordinary check guard still applies,** with R-OBL-3's
  qualifications of obligation, checker, integration, input,
  configuration and runner. A holder or proposer cannot meet their own
  check obligation. Generic submission alone is not independent
  evidence.
- **The generic path refuses v1 acts and platform kinds.** Bearer acts
  stay excluded from the ordinary signed-envelope POST route.
  Key-signed checks keep their specified authority and v2 binding
  rules.
- **Neither a pack alias nor a generic call bypasses these exclusions.**

Stage 4 still owns the production `CheckJobV2`, service signing and
prepared facts. Allowing this transport does not deliver that work.

## 5. L0: the transport adapter

**Wire formats.** `createMcpHandler` with `legacy: "stateless"` serves
2026-07-28 clients and older stateless clients from the same endpoint.
No session store. `server/discover` advertises the server's name,
version, instructions and capabilities. The deployed SDK and
specification snapshot is pinned (section 3).

**Endpoints.**
- `POST /v1/rooms/:room/mcp`: the room's MCP endpoint. One
  room per URL keeps tool lists stable per principal and lets OAuth
  bind tokens to one room. The route and its adapter are **Delivered**
  as source (section 2).
- stdio: `artroom mcp`, for local clients signing with the user's own
  key (exists).

**Authentication.**

| Method | For | How | Status |
|---|---|---|---|
| Bearer header | Agents in Claude Code, Codex, pi, scripts | A room-custody invitation, redeemed once; the token in `Authorization: Bearer`. Each harness keeps it in an environment variable or header helper, never in a committed file | **Delivered** as source |
| OAuth 2.1 | People in hosts that cannot set headers: Claude Desktop and web, ChatGPT | `workers-oauth-provider`. The room's join page may host the steps below, and keeps them distinct. Protected Resource Metadata at the standard well-known path; 401 with `resource_metadata`; the token bound to the room's MCP URL as its audience. CIMD preferred; dynamic registration only for clients without CIMD (on 2026-10-01, pi) | **Adopted** for stage 2 (`775acdd3`). Not built |
| Own key (stdio) | A person or script with an Ed25519 key file | The CLI signs envelopes; no bearer | **Delivered** as source |

**OAuth: identification, consent and admission.** Revision 3 said that
the join page is the consent page, and that redeeming an invitation
issues the token. That is corrected. Redeeming an invitation identifies
or joins a person. It is not consent to an OAuth client. The four steps
are:

1. **Identify the person.** Authenticate them as the relevant member,
   or redeem an invitation to join under the room's rules.
2. **Validate the client.** Check the requesting client, the exact
   redirect URI and the room resource. Show the client's identity and
   provenance, the destination hostname, the room and the requested
   scopes.
3. **Obtain consent** to that combination of client, resource and
   scopes. A denial or an invalid request issues no token. Remembered
   consent is reused only within the same validated identity, resource,
   destination and scopes.
4. **Issue the audience-bound credential** under the existing room
   principal and delegation model. Validate its expiry, audience and
   scopes. Then check the current member, key and delegation authority
   at each operation.

A token whose audience is room A cannot be used for room B. OAuth
tokens are not passed through to Artifacts, model providers or
application services. The exact scope vocabulary, the refresh and
revocation mechanics, and the mapping to a room principal and
delegation are a bounded design deliverable of the MCP owner, with C1
(`b538c5ea`) and N3 (`f3299ab4`). That deliverable must preserve these
decisions and the full OAuth journey. It must not assume that the
provider package completes it.

**Unchanged:** bearer roster acts are never accepted over MCP. The
legacy bearer `check` stays RPC only, and a bound declared check step
may use the generic `act` (section 4). Tokens are never passed through
to Artifacts or logged (R-WS-4).

**Errors.** As R-API-1. There are three shapes, and each stays
distinct:

| Outcome | On the wire |
|---|---|
| An ordinary room refusal | A result with `isError: false` and a structured `Refusal` |
| A tool execution failure | A result with `isError: true` and the safe structured `ArtroomError` |
| A protocol fault (bad JSON, unknown method) | The SDK's JSON-RPC error mechanism. JSON-RPC errors are only for these |

- **Advertise `outputSchema`** for every tool. The advertised schema
  must cover every shape the tool returns, because the 2026-07-28
  specification requires structured content to conform. Revision 3
  promised `oneOf` the tool's result and `Refusal`, which leaves out
  `ArtroomError`. **Proposed default:** a disjoint union of success,
  `Refusal` and `ArtroomError`, keeping the existing flat Artroom
  shapes. Match the schema representation the selected SDK supports.
  Do not assert that `oneOf` branches are exclusive unless they really
  distinguish themselves. If a reviewed SDK needs a different way to
  represent a tool error, say so, and keep R-API-1's meaning on every
  transport. An implementation review settles the exact schema. This
  plan is not evidence that a schema failed in an approved adapter. On
  `main` the eight tools that can refuse (the seven act tools and
  `workspace`) advertise `oneOf` their result and `Refusal`. On the
  candidate branch there are nine: the same eight and the generic
  `act`.
- **Every result also carries a short text form** (the headline and
  fix, as lane E does), because some clients show only text.

**Credential outputs.** The grant of a ready workspace is an authorized
credential output. It must reach the current eligible holder of the
lane and lease, through that grant and nowhere else. Other tool and
read results, ordinary text, attention, public logs, errors, prompts,
resource caches and an application's debug state must not contain its
token. A pending or failed workspace issues none. Revision 3 asked for
"no token in any result", which would ban the grant itself.

**Private reads and owner authority.** An OAuth or bearer credential is
not a direct owner or admin device session. The approved raw private
reads of a workspace, a transcript or a command need direct-key
provenance and current owner or admin authority at the trusted room
boundary. A member handle, a generic MCP read, OAuth consent or a
delegation does not meet that requirement. Other participants receive
the approved minimal status. Task controls keep their separately
signed authority, bound to the resource, action and body. MCP cannot
add owner-control power.

A browser that disconnects does not stop authorized hosted work that is
running. Revoking a device key, removing the owner or ending a
delegation follows the lifecycle and current-authority checks of C1
and C3. An OAuth refresh, a cached descriptor or a surviving MCP
connection cannot reverse those effects, and cannot substitute a new
owner. Workspace epochs, leases and the physical cleanup of credentials
stay with their existing owners.

**Caching.** Cache hints apply to the complete discovery, list and
resource results named in section 3. They do not apply to `tools/call`
in general. Revision 3 gave TTLs to tool reads; that is corrected.

- **Authenticated discovery, lists and resources are private.** They
  are kept apart by authorization context, and by whatever changes the
  result: room, policy, toolset, URI and arguments, and cursor.
- **`cacheScope` is not access control.** Keeping results private is
  Artroom's disclosure policy. `cacheScope` enforces no room
  authorization.
- **A positive TTL is a freshness hint.** It does not promise that
  authority continues after a revocation. Current private authority is
  checked whatever the TTL.
- **Lists.** Revision 3's `ttlMs` of one hour is a candidate upper
  bound. It is not a licence to reuse authority for an hour. The owner
  of the cache defines its invalidation and its current-authority
  checks.
- **Moving state** (attention, a lane's state) is stale at once:
  `ttlMs: 0` where a hint applies.
- **Immutable content** (an act, a generation, a file at a commit) does
  not make permission to disclose it permanent. A cache of authorized
  immutable content behind a read tool is a separate application
  optimization. Do not call a tool response cacheable on the wire only
  because it contains a pinned commit.
- **Credential grants and raw private resources** never go in a
  reusable shared cache.

**Size.** Every result stays under 20 KB of text (on 2026-10-01 pi's
limit, the smallest; kept as a project budget). Lists paginate with
cursors; diffs and files return a bounded slice with a "more" cursor
and a note saying so.

## 6. L1: the core profile

### Principles

1. **One tool per `RoomApi` method;** names match the API, so a reader
   of the docs, the CLI and the MCP tools sees one vocabulary. The
   named act tools are the code-review conveniences. `acts` and `act`
   are the general route for any declared act (section 4).
2. **Short names, no prefix.** The host already namespaces them (for
   example `mcp__artroom__claim`).
3. **Annotations tell hosts what is safe.** Hosts may auto-approve
   read-only tools and ask before consequential ones. Annotations are
   hints and never authority.
4. **Retries are safe.** Every act tool takes an `idempotencyKey`, and
   it is required (**Adopted**, `775acdd3`; **Candidate**, R-API-9), so
   a retry after a lost response can never record an act twice. The
   description says "any unique string; reuse it to retry this exact
   call". A key identifies a retry. It does not by itself preserve what
   the call meant; "Retries and prepared meaning" below says what must
   be kept.
5. **Descriptions are for agents.** Each says when to use the tool, the
   one or two likely refusals and their fixes, and stays under 1,000
   characters.
6. **Handles, not sessions.** Lane and lease (`McpHeld`), operation
   IDs, cursors and act IDs are passed in arguments.

the exact encodings and constraints. Every write schema requires the
caller's key.

Prompts are ready-made instructions a person can pick (on 2026-10-01,

### Server instructions

At most 512 characters, self-contained. This is a project budget
(sections 3 and 10), not a rule about what a host cuts. The
instructions say what the room is, "call `room` first, then
`attention`", and that refusals carry a fix. Before item 5 ships, they
start with `attention` and the lane and acts reads that exist. They
must not tell a client to call a `room` tool that is absent. Longer
guidance lives in the `start` prompt and the agent guide.

### Long operations

`workspace`, `land` and `operation` take `waitMs` (at most 45 s) and
return the operation's state; the caller calls `operation` again to keep
waiting. A timeout keeps the handle and leaves the outcome unresolved.
It does not mean pause, cancellation, completion or a failed side
effect. Operation IDs are designed to map one to one onto the Tasks
extension when clients support it (stage 3), with no change to their
meaning. Tasks present the existing handles and status. They do not
change what finished or who may cancel.

### Retries and prepared meaning

A required key identifies a retry. It preserves the intent only if the
prepared request is kept. Before the first dispatch, the existing
durable owner of the work must retain:

- **For every act:** the room; the principal, session or signing
  identity; `kind`, `target`, `body`, `binding` and the caller's key;
  and the exact signed envelope bytes where there are any.
- **For a pack tool:** also the resolved repository and policy
  revision, the pack revision and mapping identity, the validated
  input, and the prepared room call that resulted.
- **For a hosted task:** also the resolved meaning of the task or
  prompt and the provenance of its author, tied to the existing
  conversation, input and operation records.

Who keeps it:

| Caller | Owner of the prepared call |
|---|---|
| A client with its own key | The client. It stores the signed prepared object before sending. After a restart it replays the same bytes |
| A bearer caller | The caller. It stores its unchanged prepared call, with the binding and the original session context. The room's existing bearer path builds and signs it under that session |
| Hosted work | C3's durable ledger of conversation, input and operation |
| A local client or application server | Its own stored prepared objects |
| The MCP Worker | Nothing. It is stateless and owns no hidden conversation or retry session |

Rules:

- **No rebinding.** Neither the transport nor a resumed pack chooses a
  newer binding or a new session to make an unresolved call succeed.
- **Two boundaries stay distinct.** Settling a retained signed
  envelope without fresh authentication is one. A retry by a revoked
  bearer is another. The reviewed identity and idempotency rules decide
  each.
- **No new public outbox.** An ordinary handle may locate a prepared
  object in its existing owner, with current access checked. An
  in-memory cache of unanswered calls proves no recovery after a
  restart.
- **After a lost reply,** replay the retained call, or reconcile it
  with its recorded receipt or operation. Do not run a mapping again
  from today's pack. Do not rebuild an envelope from today's catalogue
  under the old key.
- **After `binding-stale` or `kind-undeclared`,** show the relevant
  active or retired meaning. The caller then chooses, explicitly, a
  fresh preparation and a fresh key. Nothing is signed again
  automatically.
- **An exact retry of an act already admitted** returns its original
  result under R-IDEM and R-DECL-16. It does not take the new
  declaration's meaning.
- **Unknown outcomes outside the room stay unknown.** Retrying an act,
  deduplicating attention input and deciding whether an external
  effect happened are three separate operations. Uncertain command and
  provider outcomes are reconciliation work for C2 and C3. MCP Tasks
  and wait timeouts cannot make an unknown outcome safe to repeat.

The client's `PreparedAct` and `replay` at `f6212850` illustrate this
boundary. They are **Candidate** source, not an approved delivery. A
durable outbox for every caller is not built and is not claimed here.

### Elicitation

Not used for authority. A verdict, a landing or a claim is always an
act by its signer, never a click inside a host. Consent, review and
landing stay properly authorized room operations. The one planned use
is convenience: a person using a host with elicitation can be asked to
pick among overlapping lanes before a `claim` (stage 3). Clients without
elicitation get the same choice as a refusal with a fix.

## 8. L3: application packs

**The problem.** The jam room and other applications want their own
verbs: "join a part", "send a cue", "propose a take".

*History.* On 2026-10-01 the contract had seven act kinds, and the jam
design required zero contract amendments. Revision 3 therefore treated
most application verbs as an existing act with an application's
conventions: a claim on `parts/<part>/**`, a note anchored to the
count-in.

*Now.* An application declares its own acts (section 4). A pack gives
those acts, and reads, convenient names and schemas as MCP tools. A
room on the code-review vocabulary can still map a verb to `claim` or
`note`. No application is required to.

**The design.** A pack is a JSON file in the repository at
`.artroom/mcp/<pack>.json`. Because it is under `.artroom/**`, changing
it needs an admin's approval (R-ADMIN). The room's MCP Worker loads the
packs from the reviewed active configuration, in the active policy
version. Packs are **Adopted** (`775acdd3`) for stage 2 and are not
built. A pack declares:

- **Tools.** Each has a namespaced name (`jam.join_part`), a
  description, an input schema in the restricted JSON Schema subset, a
  toolset list, annotations, and a **mapping**: a JSONata expression,
  in the same pinned profile and budgets as policy (R-EVAL), that turns
  the input into exactly one ordinary room write or read. The input
  includes the caller's required `idempotencyKey` for a write, and the
  mapping copies it unchanged into the room call. For example:

  ```json
  { "name": "jam.join_part",
    "description": "Take a part in the song. Refused if someone holds it.",
    "input": { "type": "object", "required": ["part", "idempotencyKey"],
               "properties": { "part": { "type": "string", "pattern": "^[a-z0-9-]+$" },
                               "idempotencyKey": { "type": "string" } } },
    "toolsets": ["builder"],
    "call": { "tool": "claim",
              "args": "{ 'goal': 'Play ' & part, 'scope': ['parts/' & part & '/**'], 'idempotencyKey': idempotencyKey }" } }
  ```

  This example is schematic. It shows a room on the code-review
  vocabulary, where the verb maps to `claim`. Revision 3's example
  dropped the caller's key; this one carries it. The jam has not chosen
  its first declared vocabulary, so no declared kind is named here.
  `claim` and `note` are not prescribed for the jam's verbs.
- **Resources.** Read-only URI templates over repository paths, for
  example `jam://song` → `file` of `song.json` at `main`.
- **Prompts.** Templated instructions, for example "you are the bass
  player; listen for cues on the count-in act".

**How a pack write runs.** For a jam pack whose verb maps to a declared
act, the sequence is:

1. Validate `part` and the caller's required `idempotencyKey`.
2. Resolve the retained pack's declared application act and its
   binding.
3. Compute the target and body once.
4. Persist the prepared object with its existing owner (section 6).
5. Dispatch once. The key reaches the room call unchanged.

**What keeps packs safe:**
- No code runs; a mapping is a bounded, pure expression. It cannot
  call a service.
- Each pack tool makes exactly one room call, signed by the caller and
  admitted by the room, so policy, roles and the log treat it exactly
  like the core call. `explain` shows the ordinary core outcome and the
  safe provenance of the pack and its mapping. A reviewer can trace
  what the verb meant. Credentials and raw private task inputs are not
  shown.
- A pack cannot add a role or a rule, and it cannot declare an act
  kind. Kinds come from the room's declarations.
- A pack tool's annotations can only be stricter than the core tool's.
- Core names are reserved, and pack names contain a dot.
- Installing and changing a pack reuses N5's reviewed lifecycle of
  proposal, approval, activation and regrant (`f1af7cfd`). Editing a
  prompt or a descriptor cannot grant an undeclared kind.
- A retry replays the prepared call. It never runs the mapping again
  from a changed pack (section 6).

**What packs cannot do:** keep state, call other services, or combine
acts. Those belong in an application server (L4), which handles them
through operations it owns explicitly.

**Judgement.** Packs cover the verbs the jam note lists without a
redeploy, and they make an application installable by ordinary acts, as
the jam note asks. They do need a contract amendment (section 11, item
6). The declared-acts route (**Candidate**, stage 5) gives an
application a complete route without packs, so the jam does not wait
for packs.

## 9. L4: application servers and the MCP library

An application that needs code, state or other services runs its own
MCP server in its own Worker. To make that quick, lane E's package is
published as a library with separable parts. The library is planned
for stage 2. Request N3 (`f3299ab4`) reviews the exact names and
exports, and the library has no private room imports.

| Export | Use |
|---|---|
| `coreTools(room, { toolset })` | The L1 descriptors and runners, bound to a `RoomApi` |
| `packTools(room, packs)` | The L3 tools, for an app that hosts its packs itself |
| `toMcpResult(result)` | The refusal and error mapping of R-API-1 |
| `createArtroomMcpHandler({ room, tools, auth })` | L0, around `createMcpHandler`, with bearer or OAuth |
| `descriptors({ toolset })` | Plain descriptors, for non-MCP harnesses (pi-durable extensions, Agents SDK tools, code mode) |

**Rules for application servers:**
- They reach the room through the client library or a service binding,
  under a current delegation the room issued. Every write is a signed
  act, admitted in the ordinary way.
- They may re-export core tools next to their own, so an agent needs one
  MCP URL.
- Their own tools are namespaced, and their state is theirs, never
  authoritative over the room (as the jam note already requires of its
  live layer). Their ledgers of external operations are theirs too.

**pi-durable** can use `descriptors()` and the runners directly as
pi-durable tools, without MCP; its design (request `3f23ea89`) decides.

**Real-time applications.** MCP is turn-based. A jam player, a live
dashboard or anything that must react within a second uses the room's
WebSocket `subscribe` (R-API-8), as the jam note decides, with that
route's recovery contract. MCP stays the connection for turn-based
agents and for people in chat hosts.

**Live operation for agents.** Polling is the reliable baseline: the
attention cursor, bounded waits, operation handles and ordinary
authoritative reads. A timeout or a disconnect does not imply pause,
cancellation, completion or a failed side effect. Durable input
delivery, fresh visibility scans and catch-up follow plans 007 and 008
under C3. They do not depend on the wire connection.

**Subscriptions (stage 3).** Live `subscriptions/listen` stays in
scope. It needs a reviewed design for routing from the Room to a
handler, and for recovery, because Cloudflare's notification routing is
isolate-local (section 3). Reusing a handler at module scope proves no
delivery across isolates. On reconnect the client reconciles from room
cursors and reads. A notification is a hint. It is not replay,
authority or proof that work completed.

## 10. Context cost

**The budget.** These are Artroom's own conservative budgets. They are
not claims about where a host cuts text.
- The `builder` toolset's `tools/list` stays under **3,000 tokens**,
  and every other toolset under 2,500.
- Each description stays under 1,000 characters (on 2026-10-01 Claude
  Code cut at 2,048).
- Instructions stay under 512 characters, self-contained.
- Text results stay under 20 KB, with explicit bounded slices and
  cursors.
- The budget includes the general declared route and any loaded pack
  tools. Tools-only access stays complete through selection,
  pagination and concise schemas. An unbounded catalogue is never
  shown all at once.
- CI measures the token count of each toolset's list and fails over
  budget. It measures the real shared descriptor representation with
  the documented token counter, and reports the counter's version and
  method.

**Why not one "code" tool.** Code mode suits large APIs. Artroom's
surface is small, its acts are signed one at a time, and refusals must
reach the model with their fixes. **Judgement:** plain tools, kept few
by toolsets, are clearer here. `descriptors()` lets a harness that
prefers code mode (pi's default on 2026-10-01) generate it.

## 11. Contract and protocol changes

One amendment, proposed for checker's review before any lane builds on
it. Working title: **the MCP amendment**.

1. **R-API-9:** the core tools become the 14 of section 6 that call
   the `RoomApi` of 2026-10-01, and later the 4 of item 5, in the
   toolsets of section 7. Bearer roster acts and the legacy bearer
   `check` stay excluded; a bound declared check step may use the
   generic `act` (section 4).
2. **`McpToolDescriptor`** gains `title` and `annotations`, and
   `outputSchema` is advertised.
3. **`idempotencyKey` is required** on act tools over MCP.
4. **`attention`, `workspace`, `land` and `operation` take `waitMs`,**
   at most 45 s.
5. **New reads in `RoomApi`:** `room` (whoami and summary), `diff`,
   `file` and `policy`, with their MCP tools and toolset places.

## 13. Acceptance

All seven groups of revision 3 stay. Their witnesses are corrected.

1. **Conformance.** The endpoint passes a conformance suite for
   2026-07-28 and for the legacy stateless mode, at a named SDK and
   specification snapshot: the MCP project's own suite if one is
   published for 2026-07-28, otherwise our own bounded cases drawn from
   the specification. The evidence says which. **Untested** which suite
   exists.
2. **Cold-agent tests.** A fresh agent on Claude Code, Codex (default
   settings) and pi, given only the MCP URL, its scoped credential and
   the agent guide, makes a useful change: it claims, proposes and
   lands, and follows review, landing and publication. From stage 2, a
   fresh reviewer agent reviews without a git checkout. Client
   versions, tokens, turns, refusals and outcomes are recorded.
3. **Tools complete.** Every acceptance case runs with resources,
   prompts, elicitation, Apps and subscriptions turned off. A declared
   application still discovers and submits its own acts.
4. **Context budget** holds in CI for every toolset, for the real role
   and pack descriptors and the instructions, with the measurement
   method named.
5. **Invariants: authority, retry and credentials.** Tests show:
   - A hidden tool called anyway is judged normally.
   - The legacy bearer `check` and bearer roster acts stay excluded
     from MCP, including through aliases.
   - A declared check step under another name succeeds through the
     generic v2 `act`, with qualified evidence and its exact current
     grant. An absent or stale binding, an insufficient role, a
     self-check, a v1 call and a platform kind are each refused.
   - A pack tool produces exactly one act, with the caller's key.
   - A retried act with the same key records once.
   - After a lost reply or a restart, and then a change of pack or
     declaration, the retry replays the identical prepared meaning. A
     stale meaning needs an explicit fresh preparation.
   - The ready holder gets the explicit workspace grant. Unauthorized
     callers, incidental results, caches, logs and errors disclose no
     token.
   - OAuth, when built: a consent that succeeds and one that is denied;
     a token for the wrong room; a token used after its authority is
     revoked.
6. **Schema drift.** CI fails if a descriptor and the contract
   disagree. Every advertised structured shape of success, refusal and
   error matches the contract and the shared runner, over HTTP and
   stdio. The normal and error text stays understandable.
7. **The jam pack** installs by ordinary reviewed configuration acts,
   maps the declared vocabulary the jam chose, and works from a named
   agent in Claude Code (stage 2). An upgrade keeps the old meaning,
   the history, the regrant and any unresolved work.

When subscriptions are built, add an honest case of disconnect and
reconnect.

These are boundary witnesses inside the existing implementation tasks.
They are not a sweep of every field and not a new large cross-product
suite. Unchanged reviewed source and evidence may be carried forward
only when its dependencies and the meaning of its witness are
unchanged.

### Differences between this plan and the candidate

The candidate (R-API-13 and R-API-14 on `request/test-overhead`,
decided there under `3d8a74a9`) differs from sections 6 and 7 in these
places. This note records them. It does not settle them.

- The candidate has no `triager` toolset.
- The candidate's `observer` set includes `operation`. Section 7's
  does not.
- The candidate's `reviewer` set is the default for the role `checker`.
  Section 7 gives it to members named by review obligations.
- The candidate lets a caller select any of the four toolsets by name,
  filtered by one eligibility rule. Section 7 describes the choice as a
  way to see fewer tools.
- The candidate advertises `oneOf` result and `Refusal` for the nine
  tools that can refuse: the seven act tools, `workspace` and the
  generic `act`. Section 5 proposes a union that also covers
  `ArtroomError`.

### Unresolved implementation choices

1. The exact encodings of the descriptor and error union that the
   selected SDK supports, keeping flat Artroom results and conformance
   to the public schema.
2. Where pack activation and mappings are stored, and how a prepared
   handle is encoded in its existing owner. General discovery already
   supplies the required route.
3. OAuth scope names, the mapping to principal and delegation, and the
   refresh and revocation mechanism, under the current trusted room
   authority contract.
4. The real lifetime and invalidation of the private cache, and the
   routing of subscribers across isolates, keeping fresh authority and
   catch-up from the room.
5. The named current client configurations, the conformance runner and
   the exported context counter. Historical documentation cannot answer
   these.

### When to stop

Stop and bring back a concrete design correction if integration would
need any of: automatic re-signing; omitting client consent; wider raw
private access; an excluded MCP write; a second vocabulary; or public
retry state with no owner. A limit of an SDK, or a feature a client
lacks, is not permission to narrow the adopted scope.
