# I2 base milestone: the lane forms as data, on the scope substrate

Request `efb4e323`. Branch `request/i2-lane-forms`. Written 2026-10-05.

**This is a milestone of I2. It is not I2.** The planner has ruled that
the base may be reviewed and may land while the request stays open. The
commission says that partial base work "cannot satisfy the full I2
delivery". Section 4 lists the rows that remain and whom each waits on.
This note is the producer's account. An independent review decides what
it is worth.

## 1. What is delivered, first

1. **The two lane definitions, `issue` and `change`, as data**, in a new
   package, `packages/lanes`. Each passes `validateDefinition` whole at the
   bounds of `PROPOSED_BOUNDS`, and each is pinned.
2. **The forms of the adopted scope contract that the two definitions use
   and that I1 did not have**: 38 forms, in `contract`, `bytes`, `derive`,
   `scope`, `replay` and `client` (section 3).
3. **A client handle that is typed from any declared definition**
   (`declaredHandle`, in `packages/client`).
4. **Ten scenarios** that run the two pinned definitions on real scopes,
   with stand-ins that each test names (section 7).
5. **Removal and guides**: one parked file deleted, the ledger reconciled,
   `docs/lanes.md` and a generated `docs/lanes-reference.md` (section 9).

**Under the production wiring, nothing of the lanes runs.** A scope is not
founded or created under either definition. The answer is
`unsupported-definition`. That is the design, for this reason. Both
definitions list `git-read@1` and write guards and effects of `hold@1` and
`git-read@1`. The contract's section 6.1 says that a runtime which does
not implement a capability version "answers `unsupported-definition` and
admits nothing to that scope". No code for those capabilities exists: the
authority note's successor (request `406983fe`) owns their rules and I3
builds them. A runtime that ran the other rows and skipped the capability
rows would write entries that a later, complete runtime would judge
otherwise. So the whole scope is refused, and the verifier answers the
same at the genesis. Witness: `packages/scope/test/founding.test.ts`, "a
definition that needs a capability record". This is the builder's
decision on an open question (deltas entry DJ14). The owners have not
confirmed it.

## After the base milestone: the genesis kind

**What changed.**

## After review dce192f4: the repairs

The review of the same milestone at `50bba45c` found three supported P2
source findings. Two are about how a typed value is converted where it
passes from one scope to another, and the third about a limit of the
verifier. The deltas note, section 25, has the entries DR8 to DR15 with
their controls. Each repair is its own commit. The reviewer found DR8,
DR9 and DR10. The comparison below found DR11 to DR14, and the two
readings of DR15, which are not changed.

**DR8, an item inside a record of a message.** A message names its
receiver's item by the fact of the entry that opened it. The receiver read
that fact as the item in a field and in a list, and not in a record, so a
valid record was refused `bad-field`. It now follows the handler's
declared type through records and lists, with the checks of the direct
field. Witness: `derive/test/forms-handlers.test.ts`, the handler test.

**DR9, a field of an entry of another scope.** A part that read a field
of a fetched delivery, or of a created genesis, read it through the
reader's own handler or genesis act of that name. So a record that the
source admitted could be read as the sender's fact, and a guard could
pass on it. The rule now: a field is read as the scope that wrote the
entry holds it. The reader's own entries are read by the reader's types.
A field of a foreign entry is the value in the entry's bytes, with no
type applied, and the `self` mark in it is not resolved, because the
bytes do not tell the mark from a record and the reader does not hold the
other definition. An own request that no handler received is read in the
same way. What stops working is a comparison of a field that was sent as
the mark, in another scope's delivery or creation, with the sender's
entry: it fails. Neither lane definition makes one. Witness:
`derive/test/forms-operand.test.ts`, the handler test.

**DR10, the depth limit in the settlement.** The settlement of owed texts
read a scope on from depth 0, so a chain could pass the caller's limit.
The builder decides the question that DR4 left open: depth counts the
chain of foreign facts from the target, in both phases. Each scope keeps
the depth at which it was reached, and the settlement reads it on from
there. A limit reached there is `incomplete`. The contract's next
revision is asked to state it. Witness: `replay/test/verify.test.ts`, the
settlement test, at depth 1 and at depth 2.

**DR11, a record copied into a slot.** The commit's check of a value with
no declared type followed a list and not a record, so an item inside a
record was not checked to exist. It now checks each member by its type.
Witness: `derive/test/forms-effects.test.ts`.

**DR12, equality inside a record.** Equality put a local fact in normal
form in a value and in a list, and not in a record. It now does so at any
depth. This builds what entries DF4 and DI15 left. Witness:
`derive/test/forms-fields.test.ts`.

**DR13, a presented fact in a send.** A presented fact of the sending
scope was sent as a bare number. It is now sent as its fact reference.
Witness: `derive/test/forms-operand.test.ts`.

**DR14, a message that no handler receives.** A handler for a sender
under another definition does not receive the message, yet the receiver
fetched the entries and texts that its fields name before the turn. It
now fetches none, and the verifier asks for the same texts. Witness:
`derive/test/forms-handlers.test.ts`. It is of the function that the
runtime and the verifier both call, and not of a delivery on real storage.
