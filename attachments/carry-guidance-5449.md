For a carry attempt whose state and completion are established, the following procedure follows production `packages/room/src/core.ts:1205–1302`. Extracting its deterministic selection/input logic into a pure planner shared with, or compared against, the Room would avoid a second invented definition. This is a recommendation, not an adopted API.

1. Identify the admitted operation, lane, generation and integration; select the applicable policy/checker document and the generation state at the attempt's actual reads. A prepared event supplies integration, base/tree and checker snapshots, but does not itself identify a carry attempt or its completion. Require matching ownership when using it for operation facts. `Fold.landOps` records admission, not the operation lifecycle (`packages/log/src/fold.ts:168–182`, `:353–355`, `:400–412`). The current carry lookup's fallback to any prepared event with the same integration (`verify.ts:907`) must not be treated as proof of this operation's preparation.
2. Rebuild the initial statuses for that integration, then retain the generation's obligation order. Skip non-check obligations, obligations initially met, and missing checker configurations. “Met” includes a qualifying, valid check on the integration and a still-valid carry under the policy that counts now. Use the existing qualification/status functions, with admission role, teams, authorship and flags; do not replace them with current membership tests (`packages/log/src/obligations.ts:146–177`, `:207–272`; production `packages/room/src/obligations.ts:94–125`, `:214–251`).
3. For each remaining check obligation, select accepted check evidence from this lane at generation <= target generation, in descending admission sequence at that obligation's candidate read; require `ok`, the same obligation and checker, and a different canonical integration. Unknown filtered canonical mappings leave eligibility unknown. The production candidate filter does not first remove revoked or currently unqualified evidence. Revocation can require a negative judgment; current qualification separately decides whether a stored carry meets the obligation (`core.ts:1217–1234`). For declared acts, classify evidence by its admitted check step, rather than inferring all semantic identity from an application's literal kind name; the existing renamed-check finding is not a new finding here.
4. Preserve the judged key `(lane, generation, integration, obligation, evidence act, policy version)`, which deliberately omits operation. Skip an already sealed judgment for that key, including a negative judgment. A failed prior judgment is not retried merely because another readiness attempt starts; a new policy or integration has a different key. A successful judgment can later stop counting because of revocation, changed requirements or configuration, so neither a success nor a batch-complete flag should permanently suppress later attempts (`core.ts:1213–1216`, `:1229–1234`, `:1276–1302`; `packages/log/src/obligations.ts:257–266`).
5. Read the integration tree and, for scoped inputs, the configured snapshot as production does. Missing tree aborts the carry loop; a failed snapshot read gives null and can produce a negative judgment. Rebuild evidence/from, proposal/owners, original-generation policy comparison, revocation and exact before/now check bindings. The current checker configuration, volatile flag and pinned runner supply the “now” facts; the older check's body supplies “before”. `policy.same` compares the evidence generation's proposal policy with the evaluation policy, not its check-admission policy (`core.ts:1225–1259`).
6. Evaluate each unjudged candidate with a fresh act meter; use the policy evaluator's platform conditions and rule order/stopping. Seal/account for the judgment even when the decision list is empty: platform rejection, no applicable rules, recovery purpose or no runner pin can produce zero decisions. No runner produces the exact `runner-changed` outcome without invoking policy. Within one judgment its rules share the meter and stop at the first false/error. Compare the full reconstructed context, decisions/usage and outcome; then account for the event and judged key (`packages/policy/src/carry.ts:170–203`; `packages/policy/src/rules.ts:326–370`; `packages/log/src/calls.ts:245–272`).
7. Stop that obligation's candidate loop on `res.carried`, exactly as production does, and continue with the next obligation. This is not the same as testing whether the resulting evidence qualifies for the current obligation: a carried result can still fail current qualification, leaving the obligation open on a later attempt. Negative outcomes continue to older candidates. Do not demand all candidates once one carries (`core.ts:1258–1299`).
8. Match the ordered judgments independently of recorded decision groups. A missing owed event is `decision-missing` even if its expected decisions are empty; an event that no established attempt accounts for is `decision-extra`; a supplied context differing from reconstructed facts is `context-mismatch`. Existing `CallSession` handles decisions within the matched event, but cannot alone prove event presence. Maintain only accounted-for carries when rebuilding the later land input; changing that input consistently must not hide an absent owed judgment. Attribute missing work at a boundary that establishes completion, not at the end of an arbitrary partial prefix.

Attempt timing prevents a blanket total-order rule over sealed events. This is a source fact, not a new runtime forgery proof: `packages/git/src/landing/engine.ts:234–254` calls readiness without an evaluation lock; `packages/git/src/landing/core.ts:511–522` increments the revision while prior work may be pending; `:545–563` fences only the final readiness answer. Carry transactions have already sealed before that fence. Initial statuses and each obligation's candidate list are captured before that obligation's awaited tree/snapshot work; `core.ts:1259–1261` rechecks only the individual judged key at sealing.

Consequently two attempts can begin while the obligation is open. One carries the newest check; the other, retaining its earlier open status, sees that newest act already judged, skips it, and judges an older check. A rule that rejects every later successful carry would reject this possible production interleaving. This possibility was not executed in a runtime probe here. No standalone extra-success defect is claimed. Similarly, evaluation policy is captured before awaits (`core.ts:1108–1118`), while evidence actor teams and revocation are read at each candidate (`:1233–1244`). Carry status also reads live policy metadata (`packages/room/src/obligations.ts:228–232`), which can differ from the captured document after an await. A later activation or roster entry can precede the eventual sealed judgment. Equality to the policy/roster at seal sequence is not an adequate start-state test.

| Available evidence | What can be derived | Remaining boundary |
|---|---|---|
| Fold plus a valid operation-owned prepared event and needed Git objects | Version/obligation order; admitted evidence and original authorities; prepared integration/tree/snapshots; configured pins; deterministic selection and evaluator results for an established read state | Prepared does not say when an attempt started, its policy/candidate/status read states, whether it finished, or which concurrently sealed events it produced |

| Missing Git and/or filtered preparation mapping | Envelope, obligation/checker identifiers, fixed admission facts, declaration/configuration history, known revocation/pin/volatile failures and judged-key history | Specific tree, changed-path or filtered-snapshot facts may be unavailable; report them specifically. For complete batch accounting, one of two lifecycle designs needs to make the missing facts explicit. These are alternatives for builder/planner evaluation, not changes made or adopted here:

- Publish attempt identity and ordered state anchors (operation/preparation attempt/evaluation revision, integration, policy, and the fold positions used for initial statuses/candidates and each candidate's mutable facts), bind each sealed judgment to it, and publish completion/termination. Keep the candidate order derived from anchored fold state; an unvalidated Room-supplied candidate list or context is not its authority. Completion should distinguish early waiting/retry/failed outcomes, runtime failures and tree absence. An unfinished published prefix stays pending, while a witnessed completed attempt must account for every derived judgment, including zero-decision negatives. Witnessing must happen before the reads it claims and cannot silently fence away already-sealed side effects.
- Serialize carry work per relevant operation/integration and fence its state at each committing boundary, with a published start/completion or another explicit lifecycle boundary sufficient to establish that a pass ran. Blocking overlaps alone does not prove when a pass started, completed or failed, and end-of-prefix is not such a boundary. If facts move during awaits, discard the uncommitted result and start a new anchored attempt; do not mix captured policy with seal-time roster or rewrite existing history. This would change producer lifecycle behavior and therefore needs the project's normal ownership/design process.

Existing `land-evaluated` is evidence that a readiness attempt reached reservation-rule evaluation; it can support derivation of required earlier work in an otherwise reconstructable history. It is not emitted for every attempt: readiness can return retry/waiting/failed, and `evaluateLandRules` caches by operation/input digest (`packages/room/src/core.ts:1101–1152`, `:1161–1187`). A prepared-only prefix does not owe a completed batch; neither negative judgments nor resumed work necessarily end with a new land-evaluated event. Preserve the established omission cases now, while resolving these witness/timing boundaries for the full condition rather than replacing missing-event accounting with a caveat.

Meter and context-era controls should stay explicit. Check judgments each start empty, whereas version admission's refuse/require/review-carry calls and recomputation's require/review-carry calls share their enclosing meter. Evidence qualification uses recorded admission facts; an evidence actor input keeps recorded authority role but reads current teams. Queued notify keeps its admission snapshot. Use evaluator-derived usage when rebuilding budget starts, with recorded usage compared, not accepted as authority (`packages/room/src/core.ts:752–796`, `:851–857`; `packages/log/src/verify.ts:722–773`, `:816–850`, `:939–970`; `packages/log/src/calls.ts:245–265`; `packages/policy/src/rules.ts:105–110`).
