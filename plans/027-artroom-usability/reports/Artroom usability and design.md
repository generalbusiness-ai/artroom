Artroom should let a person prepare a folder, connect it to a usable room, and work through familiar issue and change lists. **The main obstacle is the number of models a person must understand before doing useful work.** The rehearsal requires six setup commands and an operator intervention before application readiness; the browser then exposes protocol forms and internal records instead of task affordances. A clean visual treatment will help, but it must follow repairs to read fidelity, action receipts, current permissions and version identity. Adopt a local-first CLI, a durable application preset and a responsive workbench, delivered as complete slices over the existing DOM and signed-client architecture. The recommendations and preview in this report are proposed behavior; they have not been implemented or validated with users. Four bounded handoff plans define the contracts, source prerequisites, implementation order and acceptance evidence.

## Six setup commands expose the wrong decisions

The supplied rehearsal is a useful demonstration of functioning mechanisms. It is a poor default onboarding model. Its setup invokes `install --plan`, manually changes the Worker's `registerScope`, runs `install --planned`, claims a room, publishes rules JSON, and activates the issue and change definitions separately. That is **six command invocations plus one configuration intervention**, ending before an issue, proposal or content publication. From the transcript's runner clock, setup starts at 03:07:42.287Z and ends at approximately 03:08:13.835Z: **about 31.5 elapsed seconds**. These are scripted expert-run observations, not novice task times. The script reports all 26 expected-output shots matched; that establishes this particular demonstration's output, not learnability or usability. ([Rehearsal transcript](/Users/hughpyle/tmp/artroom-rehearsal-1/transcript.md:3))

The consequential burden is deciding which register, provider, namespace, signing identity, policy configuration and definition digest matter. Those decisions span local configuration, remote authority and an operator's deployment. A person trying to write a handbook should begin with their handbook. Git's familiar local workflow—make a folder, edit files, initialize deliberately—offers the right starting point. A connection to shared work should explain its effect without making every author become a platform operator.

Historical main `1eed91a` reinforced that burden. `install` creates a register with a `keys` founder policy and the operator signing key; it defaults to host `github.com` and namespace `artroom`. The friendly argument to `claim` is printed but is not in the signed `found` fields. Configuration lives under `ARTROOM_HOME`, XDG configuration, or the user's home configuration directory; it does not select a room from the current folder. `Config` contains one optional repository, and a second claim is refused once it exists. There is no `init` or existing-repository import command in main's inventory. These are distinct missing capabilities: naming a room, attaching a folder, managing multiple memberships, and importing a committed snapshot. Renaming `claim` will not create them. ([Main commands](/Users/hughpyle/play/artroom/packages/cli/src/commands.ts:270), [configuration](/Users/hughpyle/play/artroom/packages/cli/src/files.ts:18), [stored context](/Users/hughpyle/play/artroom/packages/cli/src/store.ts:52), [command inventory](/Users/hughpyle/play/artroom/packages/cli/src/line.ts:8))

Room creation inside an already configured service is the useful comparison to creating a project or board in a work app. Linear documents minimal required project fields and defaults such as the workspace's first team; additional workflow features can be opt-in. Jira separates first-time product setup from creating a board in an existing space, with permission and project-type constraints. GitHub repository creation likewise exposes a name and owner while respecting organization authority, and warns against conflicting initial files during import. None of these documents prove a competitor's complete onboarding is fast or uniformly simple. They support **separating service installation from ordinary creation**, using context and sensible defaults, and asking for exceptions only when the exception matters. ([Linear projects](https://linear.app/docs/projects), [Linear teams](https://linear.app/docs/teams), [Jira board creation](https://support.atlassian.com/jira-software-cloud/docs/create-a-board/), [GitHub repository creation](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository))

### The proposed easy path starts locally and says what changed

The following vocabulary is a design proposal, **not a runnable current tutorial**. Adopt the concepts first, then validate the names. `init` prepares a local project, `connect` attaches it to a service and room, `propose` submits selected content for review, `status` explains the room and pending work, and `publish` requests publication of an exact change. Keep `join`, `clone` and the existing low-level inspection commands. Reserve operator installation for an explicit administration path. In particular, avoid making `edit` mean “open an editor” when the rehearsal implementation submits and tries to publish a file.

```text
$ mkdir handbook
$ cd handbook
# Write files with any editor.
$ artroom init
Prepared handbook in this folder.
Files are local. No room has been created or published.
Next: artroom connect

$ artroom connect
Connected handbook to Example Workspace.
Issues and changes are ready.
Files have not been published.
Open room: <room URL>
Next: artroom propose
```

`init` must be local, reversible and repeatable. Preserve file contents, modes, the Git index, history, branch and remotes. Do not stage, commit or upload anything. Do not implicitly run `git init` merely to write an Artroom binding; decide that requirement with the actual proposal/import contract. Keep credentials and secret-bearing pending envelopes in owner-only user storage. The project attachment contains nonsecret service and immutable room identity, plus a display label. Its exact location/schema is a contract decision, not an already supported `.artroom` format.

In a provisioned service, `connect` suggests the folder basename, reuses a confirmed identity and applies a versioned issues-and-changes preset. It displays the resulting review policy in a short sentence. Independent approval for protected control files is the recommended default; a solo exception needs an explicit adopted policy. Ordinary-content review policy remains a product choice and should not be silently copied from the rehearsal. Provider names, deployment namespaces and definition bytes belong in service/application configuration. If legitimate room-creation authority or service readiness is missing, name that prerequisite and the operator action. **The current register's operator-key policy cannot be turned into general member creation by a CLI wrapper.** ([Host setup and pinned register](/Users/hughpyle/play/artroom/docs/hosts.md:27), [application preset proposal](/Users/hughpyle/play/artroom/plans/025-2026-10-07-published-pages.md:71))

For an existing Git repository, show “Create room from this repository” with the chosen committed snapshot and destination. Preserve `origin`, dirty and untracked files, worktrees and branches. Distinguish the source repository from the room's canonical destination; import does not promise synchronization or mirroring. For a populated non-Git folder, show an inclusion/exclusion summary before proposing content, and exclude common secret/configuration/dependency material by default without claiming perfect secret detection. Bare repositories, nested roots, submodules and conflicting bindings require explicit supported behavior before an executor can implement them.

Joining derives service and room from the invitation, enrolls a device key through membership, and ends with a room link and a readable clone suggestion. Multiple rooms belong in a user registry; a bound folder selects its own room. Outside a binding, an ambiguous selection must stop before signing rather than choose the most recently used room. Clone must check Git availability and an empty, writable target before minting a credential. The inspected rehearsal clone uses a one-hour default token in environment configuration and does not retain it, so normal later fetch is not automatically authorized. Renewed read access needs a supported credential mechanism, separately reviewed for custody. (Candidate `315785966:packages/cli/src/commands.ts:853–905`)

Defaults must survive failures. “Room created; application setup pending” is a useful state. A durable orchestration journal must retain each exact signed stage before transmission and its accepted fact afterwards. Interrupted attachment resumes the same remote room; failed activation resumes the same application generation. An attempted mutation with an unknown outcome must be settled before signing a replacement meaning. Main's claim/join recovery already preserves exact envelopes, identities and deadlines; the older rehearsal branch has weaker retry behavior and must not replace those repairs. `--again` intentionally creates another claim and belongs in an explicit advanced path. ([Main claim witness](/Users/hughpyle/play/artroom/packages/cli/test/claim.scope.test.ts:16), [join witness](/Users/hughpyle/play/artroom/packages/cli/test/join.scope.test.ts:13))

The defaults below retain the original historical comparison: research-time `1eed91a` main versus `315785966` rehearsal behavior. See BASELINE.md for accepted I5 reconciliation. Proposed defaults require the contracts described above and do not imply a hosted account or generally authorized room-creation service already exists.

## Work lists should answer where work stands

Historical reference `315785966` rendered the room as two tables, then supplied action accordions based on declared protocol fields. It had room, item, rules and settings routes, but no dedicated Issues or Changes list route, status controls, search, sorting or pagination. Issue controls require an `On item` value; buttons say `Sign and send <act>`. Role-granted acts can still be refused by state or guard rules. This is useful as an inspector and unsuitable as the primary interaction. The screenshot of a closed issue exposes eleven schema disclosures, including closure and reopening mechanics. The human workbench needs clear destinations and task-specific forms. ([Room screenshot](/Users/hughpyle/tmp/artroom-rehearsal-1/room.png), [issue screenshot](/Users/hughpyle/tmp/artroom-rehearsal-1/issue.png); candidate `packages/page/src/view.ts:46–56,165–185`, `main.ts:138–150`)

Use a stable shell with the room's meaningful name, a room switcher, account menu and navigation to **Issues, Changes, Pages and Settings**. Settings groups Rules, Members and Connection. Activity is justified only after a usable activity read exists; low-level task scopes do not automatically deserve a Tasks destination. Put key IDs, read sessions, digests, scope IDs and operation details behind Inspect history or Advanced actions. Preserve that evidence: progressive disclosure changes reading order, not accountability.

Conventional destination names are nouns. Action controls begin with verbs: Create issue, Comment, Assign, Close issue, Reopen issue, Request review, Approve version, Request changes, Publish change, Configure rules, Save rules and Preview. A navigation link that performs the user's intended viewing action can say View latest site or View this published version. Avoid a general “What you can do here” explanation when the controls themselves can show it. Use short sentence-case labels and a restrained number of buttons; native buttons perform actions and native links navigate. Route links styled like tabs remain navigation links, rather than acquiring inappropriate ARIA tab behavior. ([USWDS buttons](https://designsystem.digital.gov/components/button/), [APG buttons](https://www.w3.org/WAI/ARIA/apg/patterns/button/), [APG links](https://www.w3.org/WAI/ARIA/apg/patterns/link/))

Issues default to Open, with Closed and All. Changes default to Open, with Merged, Closed and All; Draft, needs review, check condition and publication condition remain independent filters. A refused publication attempt does not close its change. Filter controls expose only supported properties. Current `LaneRow` has scope, number, kind, title, state and draft: author, activity time, assignee, labels and review counts need real contracts before they can appear as reliable list metadata. Default to the actual supported number ordering until an updated-time read exists. GitHub's documented issue and pull-request pages show why separate lists, visible filtering and preserved query URLs are familiar; Linear also documents property filters and URL-preserved main filters. Borrow these patterns, rather than their unsupported fields or every workflow state. ([GitHub filtering](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/filtering-and-searching-issues-and-pull-requests?tool=webui), [Linear filters](https://linear.app/docs/filters))

The list contract must be genuinely bounded. A first page should not load every lane and its final items just to show ten rows. Specify kind, supported filters, stable sort and page limit; return an opaque continuation bound to the room/query/read watermark, authoritative or advisory provenance for each row, completeness and qualified count information. Expiry or changed-query cursors get explicit restart behavior. Resolve indexes through actual authority; a directory's stale copy can appear as “Last known status” or “Status unavailable”, never freshly canonical. Global counts require a supported count read and cannot be inferred from the loaded page. Search that covers only loaded items must explicitly say so; the desired product is room-wide searchable pagination through a reviewed query/index contract. Adding a client-side status segment over an unbounded scan is insufficient. (Historical `315785966` `packages/page/src/data.ts:212–234`; [current bounded scope reads](/Users/hughpyle/play/artroom/packages/scope/src/reads.ts:216))

Shareable URLs carry room, destination, filter, query, sort and continuation/version selection as appropriate, without credentials. Reload and Back reproduce the same filter intent; returning from detail restores position. Active filter chips and Clear filters make zero matches distinct from an empty room. The empty room offers one relevant authorized creation action. A partially loaded list retains known rows, says how much was read, and offers Retry failed section. A removed member gets access-loss recovery rather than an empty list. Preserve drafts through navigation and failures.

Issue detail must resolve linked closing changes to readable numbers/titles where supported. Conversation must distinguish missing, redacted and unreadable text. Destination judgment against current rules and membership remains authoritative.

## Truthful outcomes must precede visual polish

The largest correctness risk in the proposed redesign is making a partial projection look certain. These are historical `315785966` observations; I5 has since repaired enumeration/destination failures, while text distinctions, partial presentation and qualified fallbacks remain open. Historical `315785966` `itemsOf` stopped silently after a failed page or 100 pages, `textOf` mapped refused text to null, `listLanes` fell back to advisory directory state, and `publicationsOf` returned an empty map on an unreadable destination. Historical `315785966` history had a 1,000-page ceiling without exhaustion metadata. These are inspected code paths, not failures reproduced in the supplied screenshots. The result can imply no comments, no publication or a complete list when the actual state is unreadable or partial. Every data read needs a typed outcome carrying head/provenance, completeness, continuation and failure. **Unavailable is not empty, and unreadable publication is not no publication.** (Historical `315785966` `packages/page/src/data.ts:105–122,225–230,351–373`)

The historical `315785966` submission had a separate loss of evidence; accepted I5 now preserves returned answers across failed refresh in memory, with durable reload/outbox work still open. At315, `act` received the scope answer and awaited summary before returning it; failed refresh caused `main.ts` to delete the last action. That could discard a known answer. Preserve I5’s memory-only repair and extend it through the adopted durable interface, retaining the original envelope and draft with independent observation status. Across navigation or reload, show “Submitted; unable to refresh” with Check status when acceptance is known, and “Outcome unknown” when transport did not reveal acceptance. Do not offer a blind retry that signs another irreversible intent. Reuse the I5 memory-answer witness; do not implement that repaired invariant anew. (Historical `315785966` `data.ts:549–579`, `main.ts:71–85`)

Historical `315785966` cached room read membership standing once; accepted I5 still requires fresh-standing work. Session renewal does not refresh it. A revived screen can show obsolete permission affordances after reassignment, revocation or key changes. Refresh standing when resuming the room, after membership changes, and before sensitive workflows; use a bounded reread policy whose age is visible in diagnostics. Distinguish actual permission refusal, session failure and temporarily unreadable authority. Relevant unavailable actions can stay visible with a reason; irrelevant administration stays hidden. The backend still judges every act, so stale affordances are not evidence that unauthorized execution succeeds. (Historical `315785966` `data.ts:91–96,196,528–537`, `main.ts:64–68`)

Use three independent axes. **Canonical lifecycle** tells whether an issue/change is open, closed or merged. **Publication attempt** tells whether a particular request is intended, committed, unknown, refused, aborted or confirmed published. **Readiness and observation health** explain review/check requirements and whether current authority/evidence can be read. Do not derive one from another. Approved is not published; a confirmed judge operation is not publication; zero required checks is not a passed verification. A refused path should produce “Not published. This path is outside the room,” with a supported corrective action. If path editing is unavailable, explain that a corrected proposal is needed rather than offering an unchanged retry. Keep exact reason codes in details. Historical `315785966` high-level states omitted generic/path/out-of-date refusals, and the supplied refused screen puts `effect confirmed` above the real failure. ([Refused change screenshot](/Users/hughpyle/tmp/artroom-rehearsal-1/change-refused.png); candidate `states.ts:46–65`, `view.ts:97–118`)

Preview needs a real subject. The following315 links are historical: I5 now suppresses invalid proposal links and explicitly leaves immutable version rendering unavailable. Every historical `315785966` version's `siteAddress` pointed to `HEAD`, including an invalid `../outside.md` proposal. HEAD is the latest published branch, can move after a change, and is cached for 60 seconds. Preserve I5’s latest-site labels and invalid-path suppression; they are existing regressions, not new copy/guard tasks. “Preview version 5” requires exact proposal bytes and an isolated render contract. “View this published version” requires the confirmed immutable commit, not HEAD with a nicer label. Historical `315785966` site routing resolved branches/tags/HEAD rather than supplying an arbitrary commit contract. Its public-by-directory-ID behavior must be acknowledged; a members-only preview or privacy switch cannot be implied by mock controls. Protect the signing-key origin from untrusted rendering and retain escaping, CSP, content limits and redaction. (Historical `315785966` `data.ts:330–331,404–406`, `scope/src/site/route.ts:5–9,42–43,50–65,308–312`)

## One visual system should support complete tasks

Use a quiet neutral canvas, white surfaces, a calm accent, thin separators and very little shadow. Titles, rows and spacing create hierarchy. Avoid giant onboarding heroes, decorative dashboards and equal-weight card walls. Reading content stays near 70 characters per line; review and lists can use more width. Keep paths/code monospace, but let the surrounding product use ordinary text. The token values below are proposals. Reported color ratios in the research notes were calculated for flat pairs; actual components, dark themes, focus rings and forced colors still need verification.

WCAG 2.2 AA is the conformance target across complete critical processes. Its 24px pointer-target criterion has exceptions; the **44px product target exceeds that minimum**. Normal text needs 4.5:1 contrast, essential non-text indicators 3:1, and reflow reaches the equivalent of 320 CSS pixels. Sticky actions must not obscure focus; the proposed product rule requires full focus visibility. No feature may require dragging without a single-pointer alternative. These standards guide implementation but do not establish conformance from screenshots. ([WCAG 2.2](https://www.w3.org/TR/WCAG22/), [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [focus visibility](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html), [dragging](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html))

Retain native labels, links, buttons, disclosures and selects. Add a skip link, visible active navigation, coherent heading structure and associated validation messages. Focus moves to the destination heading after navigation, returns to the trigger after closing a dialog, and survives refreshed sections. A modal contains focus and supports Escape; route changes should not rebuild the whole form and discard input. Announce concise loading/submission/outcome messages through a status region, rather than repeatedly announcing an entire work list. Authentication allows paste and assistive mechanisms. Touch users have the same tasks without hover; virtual keyboards, rotation and safe areas cannot hide the composer or its submit control. ([APG dialogs](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [accessible authentication](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html))

### Acceptance measures outcomes rather than attractive screenshots

All targets here are proposed and unmeasured: provisioned-service room creation within two minutes and at most two required decisions excluding necessary authentication; first issue within 45 seconds given its content; finding an open change needing review within 15 seconds; understanding publication refusal and the useful next step within 20 seconds. Treat zero observed wrong-room writes, unintended-version approvals and false publication beliefs as release conditions for the affected workflow. Later validation aims for at least 90% unassisted critical-task success, but small formative studies must report raw n/N and cannot establish that population rate.

Start with six to eight likely users per formative round, including Git-familiar newcomers, work-app users unfamiliar with Git, mobile users and people using keyboard or assistive technology. Separate service bootstrap, ordinary room creation, import and member joining.
