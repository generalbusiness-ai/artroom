## Method

- **Cloudflare sends one periodic sample a minute for each active object.**
  The sample is stamped with the *start* of its interval. For example, the
  invite at 16:39:15 is in the sample stamped 16:38:39, which is 16 rows,
  and not in the one stamped 16:39:39, which is 7. An eviction restarts the
  interval, so a short sample can occur.
- **Acts are 150 seconds apart.** The driver runs each act, then waits 150
  seconds, during which only background work happens. Setup steps wait 90
  seconds.
- **Each sample belongs to one window.** That window is the one that holds
  the sample's interval end. So the act, its deferred work (pin, preview,
  landing operation) and at least one quiet minute are in the act's window.
- **The act's rows are the window's total minus the baseline.** The
  baseline is the smallest non-empty sample in the window: a quiet minute.
  The act's rows are the total minus (non-empty samples × baseline). Reads
  use the same rule. The code is `windowTable` in `../rows.mjs`, and
  `rows.cases.ts` tests it.
- **What the baseline is.** In every quiet minute the room wrote 7 rows: one
  log publication of the previous checkpoint (see Finding 1). Some acts end
  the minute's publication early or late, so a window can vary by about ±3
  rows. Compare `invite` (9 in one run, 12 in the other) and `release`
  (21 and 27).

## Findings

1. **An idle room publishes its log once a minute, forever.** Each
   publication seals a `checkpoint` entry. That entry is itself unpublished,
   and `publicationDue` makes it due a minute later. Room
   `room_1741490181…` sealed a checkpoint about every 62 s from 16:36:42 to
   the end of its run.

   The cost is 7 rows written a minute: 420 an hour, or 10,080 a day, for
   each room. Its reads grow by about 16 rows per log entry, so the reads
   in a minute grow as the log grows. The run that recorded the most reads
   was the measured room (`room_872e0b20…`): 359,674 in the hour from 17:50
   to 18:50.
2. **Rooms whose repository was deleted keep writing.** Smoke cleanup
   deletes each room's repository. Afterwards the room's log head stops
   moving: `room_5c1bb798…` is at head 16 with entries published through 15.
   Yet each such room still writes about 12 rows a minute (717–720 an hour)
   and receives about 12 requests a minute.

   This looks like a failing publication retried on the 5-second loop. That
   is an inference: I could not read the room's `meta`, and alarms do not
   appear in the invocations dataset, so where the 12 requests a minute come
   from is not identified.
3. **The background is most of the spike's writes.** In the clean smoke,
   983 of the 2,284 rows came from the 15 older rooms. In the hour from
   17:50 to 18:50, 17 rooms wrote 11,285 rows and read 2,249,250. Every
   room that is made adds to the background.
4. **`attend` reads the whole attention table on every insert.** It counts
   the entry's existing items with `SELECT COUNT(*) FROM attention WHERE seq
   = ?`, and no index covers `seq`. The same is true of the nonce cleanup
   (`DELETE FROM nonces WHERE expires_ms < ?`) on every signed request.

### The background after the fix

Every quiet control window in these runs wrote 0 rows, with one exception.
The first `check` run's "before" window wrote 2: it held that run's pin
tick, because the switch was still set. The clean smoke wrote 1,270 rows.
Its three rooms wrote 1,258 of them (489, 442 and 327) and the registry
wrote 12. No other room on the spike wrote anything.

Two limits apply to every figure in this section:
- **Invocations per minute cannot be rebuilt.** The run files keep the
  storage samples but not the invocation rows.
- **The lookback is an assumption.** The gate's totals count storage
  samples stamped up to 120 s before a window. Assuming no sample covers
  more than 120 s is an assumption about the provider, not a measurement
  (measure/README.md, "The sample-interval assumption"). Before the fix, 983 of the
smoke's 2,284 rows came from idle rooms. The ceilings were re-grounded on
these runs (measure/README.md, "Ceilings").

## Known, not yet measured: lane C's publication tokens

After mint lane C lands (the checker's review b84aead9):
- a failing log publication mints 11 canonical tokens each time it
  retries;
- each mint writes 4 ledger records, so a retry costs about 44 rows
  (11 × 4, before any index multiplier);
- the idle-write fix's backoff allows about 12 retries an hour, so that is
  about 528 rows an hour for each room whose publication is failing.

This is arithmetic, **not a measurement**. Lane C is not on main, so it
cannot run on the spike. Measure it once lanes B and C are deployed, and
check it against `HOURLY_BUDGET`'s 3,600 rows per object.
